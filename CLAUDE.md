- **`wsl_keepalive.rs` — the Arch backend can host a server at all (2026-08-05).** WSL powers `dml-arch` off ~15s after the last session INTO it exits (see the Gotchas bullet — that is the mechanism, this is the fix). Rust holds ONE `wsl.exe -d dml-arch -u dml --exec /bin/sleep infinity` while the server is meant to be running. **Not the 7s frontend poll**, which measurably works and is still the wrong owner: it is a `setInterval` in a webview that HIDES TO TRAY on close, which is exactly where Chromium throttles timers past the 15s budget, it self-skips on `!refreshing`, and nothing in that file says a server's life depends on the interval (the `lifecycle_steps_for_mode` shape). **Intent, not a timer:** `games_start`/`games_restart` declare it BEFORE the work (the command is itself a session, so the clock starts when it exits) and `games_stop` AFTER (releasing first starts the clock mid-`down`). A positive status push ADOPTS a server a previous session started; a negative one deliberately does **not** release — `stopped`/`crashed`/`soap_unreachable` is exactly what a restart looks like from outside, the `restarting` suppression flag lives only in the webview, and holding through a crash is what lets `restart: unless-stopped` put the stack back. So the only routes to "meant to be down" are an explicit stop, a backend change and launcher exit, all of which release — which is what stops an orphaned holder pinning ~1.4 GB of VM. **Arch AND Wsl** (Task 1 of `docs/superpowers/plans/2026-08-05-server-survival.md`, 2026-08-05: both drive the SAME `dml-arch` distro through the same `runner::DISTRO` constant, so both get the identical 15s bug and both now get the holder — `Wsl` is also the default and the only backend the Settings dropdown offers, so it is the backend the user's real server actually runs on), as a `match` so a new backend is a compile error, not a silent opt-out; Native needs nothing (`com.docker.backend` already holds `docker-desktop`). **Never leaks:** `RunEvent::Exit` releases; the impolite exits are covered by a `KILL_ON_JOB_CLOSE` job object bound with a bare kernel32 `extern "system"` like `power.rs` — PROVEN with a control (same harness without the job: the holder SURVIVED an abrupt parent kill; with it, it died). `release()` hands the child to `dml_core::proc::abandon`, never `wait()`s it, because the watchdog holds the state mutex while releasing. **The bound is checked BEFORE the attempt, not in the error arm** — the error arm is the obvious placement and only bounds a session that will not SPAWN, while what a sick distro actually produces is a `wsl.exe` that starts fine and exits a moment later, which re-spawned forever (`a_holder_that_always_dies_immediately_also_hits_the_bound` found it on its first run). Reporting: `wsl_keepalive_status` re-derives the verdict from live state and a shell banner names the reason AND the consequence; re-read on mount as well as on the event, because a module-level store dies with a webview reload (the soap-autosetup lesson). Live gate: `cargo test -p launcher --lib wsl_keepalive::tests::live_ -- --ignored --nocapture` proves BOTH halves — survived 62.1s (4.1x the deadline), died 16.5s after release. Half one alone would pass against `wsl --list` polling, which is measured not to work.

- **THE ARCH WSL BACKEND — the second Rust route, and it is DORMANT BY DESIGN (branch `feat/arch-wsl-backend`, 2026-08-04).** Everything above assumes Docker Desktop on the Windows host. This branch adds the other route: `dockerd` running inside a `dml-arch` WSL distro the launcher creates and provisions itself, with the Rust `dml-wow` binary running INSIDE that distro (`DmlRunner::arch()` = `wsl.exe -d dml-arch -u dml --exec dml-wow`). What landed: `dml-core`'s `distro` (pure `wsl --install`/first-boot step list), `setup`'s Arch chain (`probe_arch_with`/`derive_arch`: WSL → distro → **prepared** → dockerd → `dml-wow` → a title), `Backend::Arch`, and the installer payload's Linux ELF (`payload::DML_WOW_BIN`). The ONE exception is `payload::DML_WOW_BIN`: `provision.rs:229-244` is a live production install step that deploys the ELF to `/usr/local/bin/dml-wow` at 0755 whenever a release stages it. It is *deployed* and then *never invoked*. The four gotchas below are the reasons the rest is dormant, each paid for once:
  - **THE DEFAULT DELIBERATELY STILL POINTS AT THE BASH CLI (user ruling, 2026-08-04, AMENDING the spec).** `from_override` maps unset/empty/unrecognised/`wsl` → `Backend::Wsl`, `detect` can NEVER return `Arch` (exhaustively pinned), and `arch` is an explicit env/`launcher.json` opt-in. The reason WAS a command-vocabulary mismatch — the launcher spoke the bash CLI's verbs and `dml-wow` understood none of them. **THAT PORT SHIPPED on 2026-08-05** (`dml_core::vocab`, 107 call sites: 74 translated, 33 falling back to the bash `dml` in the same distro), `command()` now appends `--json` only for the bash target, and `dml-wow` gained `games-list`/`games-status`. What still holds the default is (a) the user's own timing ruling, which has not been revisited, and (b) the setup chain: `probe_arch_with`/`derive_arch`/`dml_core::distro` still have ZERO production callers, so an Arch user has no first-run path. Do NOT cite `the_arch_runner_is_not_a_drop_in_for_the_bash_cli` as a guard — that test was REPLACED by `the_arch_runner_now_speaks_dml_wows_vocabulary` (`runner.rs:718`), which asserts the opposite property. NB `startup.rs` must export `"arch"` (not `"wsl"`) for an Arch resolution, or a `launcher.json` opt-in is silently inert — pinned by `every_backend_round_trips_through_the_value_we_export`, since collapsing that arm was invisible to all 487 Rust tests.
  - **The two first-boot bugs the LIVE GATE found, both on a genuinely fresh image.** (1) `/etc/sudoers.d` does not exist until the `sudo` PACKAGE is installed — `sudo` is `Required By: base-devel`, not `base` — so the original sudoers-before-pacman order died with `No such file or directory`. (2) A fresh Arch WSL rootfs has **no initialized pacman keyring**, so the very first `pacman -Syu` of any kind fails with `required key missing from keyring` until `pacman-key --init` AND `--populate archlinux` have run. Order is now `wsl-conf → restart → useradd → pacman-key → pacman-sync → sudoers → docker-group → docker-enable`, each edge pinned as a RELATION rather than a copy of the list.
  - **The restart is a STEP, because systemd only becomes PID 1 on the next boot.** `first_boot_steps` returns `FirstBootAction::{InDistro, RestartDistro}` — an enum, not a `restart_after: bool`, so a consumer that iterates the Vec cannot silently skip it (a match missing the arm does not compile), and `RestartDistro` carries the real `terminate_argv` so the Vec is executable as written.
  - **"Registered" is not "prepared".** Provisioning is eight steps and creates the distro at step 2; if it then dies, the dockerd probe runs `systemctl is-active` as a user that does not exist. That used to read as `DockerStopped` ("start the container engine") on a distro with no engine, and `NoDistro` was unreachable. Hence `SetupState::DistroUnprepared` + `SetupStep::Prepared` between Distro and Engine, decided by `command -v docker`, and `classify_arch_dockerd` now treats only exit **3** (systemd's documented "not running") as a stopped engine. Also: `derive_arch` reports `EXPECTED_ARCH_CLI_CONTRACT` (`dml-json-v3`), never the bash CLI's `EXPECTED_CLI_VERSION` — they are different axes and the field is rendered verbatim.
  - **`payload::resolve` reports `dml_wow_bin_present` but does NOT gate on it**, and the removal point says when it goes back (a release step that stages CI's Linux artifact AND the Arch backend being wired). Nothing stages the real ELF today, so gating made `present` `Tri::No` on every ordinary build — which stopped `provision_with` deploying the WORKING backend and withdrew the first-run "Set up backend" button in favour of advice that was false for every copy of that build.

## Gotchas

- **WSL POWERS A DISTRO OFF ~15s AFTER THE LAST SESSION INTO IT EXITS, whatever is running inside (2026-08-05, measured).** WSL 2.7.10 terminates the instance ~15s after the last `wsl.exe` client session *into that distro* exits — it took `dml-arch` down with **1,948 bots live**. Eight unattended runs: **14.7–14.9s, spread 0.2s** — not a "sometimes". The guest journal names the caller: `poweroff requested from client PID 577 ('systemctl') (unit init.scope)` = WSL's own init; `dockerd` then logs `Daemon shutdown complete`, which is why the containers looked innocent (`OOMKilled=false`, `ExitCode=0`) and every crash-shaped theory failed to fit. The incident's 25s vs the idle 15s is one event: 15s timer, then WSL's 10s grace expiring because systemd could not stop 1,948 bots in time → `reboot(RB_POWER_OFF)`. **`vmIdleTimeout` is a SECOND, independent stage and not the one that matters** (it governs when the *empty VM* exits, measured at distro death + 61.8s): tested directly, `vmIdleTimeout=-1` still died at 14.8s and then pinned the VM forever — it fixes nothing and destroys the only thing `Backend::Arch` wins. **No config key exists anywhere** (`instanceIdleTimeout`/`distroIdleTimeout`/`keepAlive` all rejected in `[wsl2]` AND `[experimental]`, proven with a positive control; `wsl --manage` has no lifetime option; `/etc/wsl.conf` has none). The ONLY lever is holding a session: a distro session every 7s holds it (stop polling → dies 14.0s later), a **`wsl --list --verbose` poll every 7s does NOT** (dead at 14.8s despite 8 polls — only a session *into the distro* counts), and every 20s does not either. `restart: unless-stopped` does not prevent the outage, it makes it *self-healing on next touch* — so the server is up whenever the user looks and down whenever their friends connect. **FIXED 2026-08-05 by `launcher/src-tauri/src/wsl_keepalive.rs`** (see the launcher/ section) — and NOT via the frontend `setInterval(7000)`, which lives in a WebView2 webview that hides to tray on close, exactly where Chromium throttles timers past the 15s budget. **What the fix buys is "the server runs while the launcher runs", and nothing more.** Unattended hosting — server up with no DML process on Windows at all — is not achievable on this backend by any mechanism the investigation found, because something on Windows must hold the session; Docker Desktop gets it by running a background service the user installed for that purpose, and matching it means shipping a Windows service or scheduled task. Do not read "keep-alive" as "the server survives closing the launcher". Measuring this needs an oracle that never calls `wsl.exe` in the window (polling with `wsl --list` measures the harness — which is also why `wsl --list --verbose` is the one probe a keep-alive test may use: it is measured NOT to hold), and the workload must be a **systemd system unit**: WSL tears down the processes of a session when its client detaches, so a `setsid`/`nohup` job from a `wsl.exe` call is not a proxy for the server (whose containers are children of `dockerd`). Detail + launcher spec: `docs/superpowers/plans/2026-08-05-wsl-distro-lifetime.md`.
- **TWO RESOLVERS FOR ONE VALUE, and only the FALLBACK disagreed (2026-08-04, live smoke).** `dml_wow::config::ConfigReader::title_dir_from_env` carried its own copy of the games-dir lookup, falling back to `PathBuf::from(".")` — the CURRENT WORKING DIRECTORY — while `dml_core::compose::games_dir_from_env` and bash's `${DML_GAMES_DIR:-$HOME/games}` (`cli/src/00-head.sh:9`) both fell back to `$HOME/games`. Nothing exports `DML_GAMES_DIR` inside the distro and a Windows-side value does NOT cross `wsl.exe` (no `WSLENV` entry), so the fallback is what runs, and the launcher's cwd is never the games dir. A missing title dir makes every file-backed read fall through to REGISTRY DEFAULTS, so `wow config list` answered `ok:true` with 11 of 66 settings that are not the server's (rates 3→1, `bots.population` 2000→500, `ahbot.character` 2501→0) — the shape right, the numbers wrong, no error to notice. ~20 call sites route through that one helper, in three shapes: honest `NOT_FOUND` refusals (`config files`, `commands`, `accountwide get`), silently wrong `ok:true` payloads (`config list`, `tuning list`, `module list` — incl. `ale_ready` true→false and a custom module vanishing from the inventory), and the DB verbs dialling **3306 instead of the title `.env`'s port** (the whole Dashboard/Item DB/Characters/Bots surface). **`dml_core::compose::games_dir_override()` is now THE ONE read of `DML_GAMES_DIR`**; `games_dir_from_env` (override+fallback) and `title_dir_for_id` (join) sit on it, and `title_dir_from_env` is a one-line delegation. `install_native::games_dir_for_install` keeps its REFUSAL — re-examined, not assumed: `home_fallback` is `None` on Windows by construction, which is where install-native runs, and `install_id` hashes the absolute path, so an inferred dir is a silent double-install. **The 18 parity suites could never have caught this and still cannot** — they build readers with `for_title(<explicit dir>)` specifically to avoid the process env (`status_parity.rs:178` says so), so the divergence lived where no harness looks. The guard is therefore STRUCTURAL: `startup.rs`'s `games_dir_reader_scan_tests` pins an EXACT map of production readers (compose.rs 1, startup.rs 1) by scanning comment-stripped, `#[cfg(test)]`-stripped source for real `var("…")`/`var_os("…")` call shapes — brace-matched cfg(test) removal (NOT cut-at-first: `engine.rs` and `lib.rs` have two test modules with production code between), a runtime directory walk (a fixed file list cannot see the new file a second resolver arrives in), a floor, and known-positive/negative probes. Windows CI only, like `vocab_coverage_tests`.
- **A detector with ONE signal fails OPEN, and nothing about the output looks broken (2026-08-01, mirrored bash↔Rust).** Every bot-vs-human check asked a single question — is the account in `acore_playerbots.playerbots_account_type` with `account_type IN (1,2)`? mod-playerbots populates that registry ITSELF, and on the freshly built `native-test` install it was **empty** (0 rows; `playerbots_random_bots` and `playerbots_account_links` too) while 1000 bot characters existed on 100 `RNDBOT*` accounts. `account NOT IN (<empty set>)` is TRUE for every row, so Home listed all 1000 bots as real players while "Bots online" read 0 — measured old-vs-new on that live DB: humans 1000→0, bots 0→1000. Bot identity now lives in ONE place per surface (`crates/dml-wow/src/botid.rs`, bash `_bot_prefix`/`_bot_account_where`/`_human_account_where` in `cli/src/30-db.sh`) and takes EITHER signal: registry membership **OR** `acore_auth.account.username LIKE '<AiPlayerbot.RandomBotAccountPrefix>%'` (default `rndbot`, `.conf` → `.conf.dist` → default, env `DML_BOT_ACCOUNT_PREFIX`). Three rules, each load-bearing: an **empty** prefix is refused (it would compile to `LIKE '%'` and call the whole family bots — the mirror-image failure), `%`/`_`/`\`/`'` are escaped so a custom prefix cannot widen the match, and stats' schema-probe failure now degrades to prefix-only instead of `0=1` ("this box has no bots" is a lie on a box that has them). The Home "Players online" NUMBER came from the same incident but has a different cause: SOAP `.server info` "Connected players" counts bot sessions by design, so the number now comes from the bot-free DB list (refetched each poll) and the raw SOAP figure survives only as a labelled "Sessions (incl. bots)" diagnostic row.
- **A Linux container CANNOT run the title installers (proven 2026-08-01, negative result).** A container with the docker socket mounted DOES drive the host daemon - but a nested bind mount silently resolves against the HOST filesystem, so `./modules:/azerothcore/modules` arrives as a path that does not exist there, and **a bind mount to a missing path is not an error, it is an EMPTY DIRECTORY**. The server then boots without its modules and looks healthy to every check we have (the recorded "boots a silently wrong server" class). Passing Windows host paths works, but `docker compose` computes absolute paths from ITS OWN cwd, so the installers would have to be patched - and using them unmodified was the whole appeal. Docker Desktop's WSL integration has none of this, which is why the `.sh` route uses a distro. `docker-desktop` itself has **no bash at all**, so it can never host them.
- **A test that scans source for a banned string must strip COMMENTS first.** Bit twice on 2026-08-01: `feature-keys.test.ts` parsed a comment containing a lock call as a call site, and `Test-InstallerNative.ps1` read the installer's own explanation of why it never runs `wsl --install`/`pacman` as evidence that it does. Fix: scan the token stream (PowerShell) or require a real call shape - never a raw grep over the whole file.
- **Anchor an ordering test on the REFUSAL, not on "X appears before Y".** `Test-InstallerNative.ps1` compared the first `Get-FileHash` against `Move-Item` to prove a download is verified before install - vacuous, because the function opens with an unrelated hash check, so the exact mutation it existed to catch stayed green. The invariant that holds is `throw` before `Move-Item`.

- **Line endings:** bash inside WSL chokes on CRLF. `.gitattributes` forces LF for `*.sh`, `*.bats`, `*.bash`, and `cli/dml`; keep new shell files LF.
- **PowerShell 5.1 + UTF-8:** BOM-less `.ps1` files containing non-ASCII (em dashes) mis-parse under the ANSI codepage. `cli/tests/windows-smoke.ps1` carries a UTF-8 BOM on purpose; keep BOMs on any non-ASCII `.ps1`.
- **Rust toolchain PATH:** Rust 1.97 MSVC is installed per-user but `%USERPROFILE%\.cargo\bin` may be missing from a fresh Claude shell's PATH — use the full path or prepend it per call. MSVC Build Tools 2022 (C++ workload) and Node 22 are installed; WebView2 present.
- **`bats tests/ | tail -40` reports the exit code of `tail`, always 0.** Cost a false "all 826 pass" on 2026-08-01: the tail happened to end on passing tests while `wow-stats.bats` was red the whole time. Redirect to a file and read the code (`bats tests/ > out 2>&1; echo $?`), then `grep -c '^not ok' out` — never judge a bats run by a piped tail. Same trap for any `cmd | tail`/`| Select-String` in PowerShell.
- **NEVER run bats and the cargo parity suites at the same time:** every bats `setup()` runs `bash cli/build.sh`, which REWRITES `cli/dml` in place, while the Rust parity suites spawn `bash cli/dml` as their oracle. Overlap makes bash read a half-written file and fail with `cli/dml: line NNNN: syntax error: unexpected end of file` — a red suite that looks like a real regression and is not (hit 2026-07-28 during the round-2 merge gate). Run them sequentially.
- **A test-double whose "override" is silently ignored is a vacuous-pass generator.** Two instances found the same day (2026-07-29), both in harnesses that looked obviously correct: (1) `install_native.rs`'s `FakeIo` registered scripted answers by pushing onto a `Vec` and resolved them with a FIRST-match scan, so every reply a test registered after the shared `happy_io()` builder was unreachable — 7 tests were asserting against `happy_io`'s answers and reported the ENGINE as broken when the engine was fine. Fixed by replacing same-key entries in place (`FakeIo::set`). (2) `cli/tests/helpers/env.bash`'s tailscale stub used `${DML_STUB_TS_UP_URL:-<default>}`, and `:-` substitutes the default for an EMPTY value too — so a test that set it empty to mean "printed no URL" still got a real URL, and the test proved nothing. Use `${VAR-default}` when empty must be honoured. Rule: after writing a test that overrides a shared fixture, MUTATE the production code and watch it go red — an override you never proved took effect probably didn't.
- **Build memory:** `.cargo/config.toml` pins `build.jobs = 8` and the root `Cargo.toml` sets `[profile.dev] debug = "line-tables-only"` (deps: none). Uncapped, cargo fans out to the logical CPU count (32 here) and each `link.exe` holds 0.5–1.2 GB, pinning RAM at 100% on a 31 GB box that also reserves 16 GB for WSL2. Don't run `cargo run` (tauri dev) and `cargo test --workspace` at the same time — same `target/` lock, double the peak. Changing either setting forces one full rebuild.
- **`wsl.exe --` RUNS A SHELL; `--exec` does not.** Verified 2026-07-28: `wsl -d dml-arch -u dml -- printf '[%s]\n' 'a;whoami' 'b$HOME' '*'` split on the `;`, expanded `$HOME` and globbed `*` against the cwd; the same call with `--exec` printed all three back verbatim (spaces survive either way, so the bug hides until a path carries a metacharacter). The production spawn `wsl.exe -d dml-arch -u dml -- dml <cmd> --json` and the `dml_core::setup` probe chain deliberately keep `--` (that is the documented contract, and their args are our own literals). Anything passing a HOST path or user text through wsl.exe must use `--exec` and real argv — see `launcher/src-tauri/src/provision.rs`, where sources come from wherever the user installed the launcher.
- **Windows→distro path translation: ask `wslpath`, never do string surgery.** `C:\x` → `/mnt/c/x` only holds for the default automount root (`/etc/wsl.conf` can move it) and has no UNC form at all. `provision.rs` translates the resource dir once via `wsl --exec wslpath -a -u` and joins every source onto the answer.
- The `games` namespace is JSON-first: `games list`/`status` always emit JSON; only `games start|stop|restart` have a text mode. Legacy top-level commands (`list`, `status`, `start`, …) keep their exact text output — the old C# tray parses it.
- `dml-start.sh` hook: `games start|restart` run `<compose_dir>/dml-start.sh <mode>` when present+executable (avoids re-running ac-db-import on restarts).
