## Rules that hold everywhere (do not move these into a nested file)

- **A fix on ONE surface only half-ships.** bash `cli/` and Rust `crates/` mirror each other across the whole SOAP/DB/lifecycle surface. When you change behaviour on either, change it on both and pin it on both — the `logsnap`, boot-loop, Tailscale, stack-conflict and bot-identity incidents were all "fixed" on one side first. Details in each nested file.
- **NEVER loosen the raw-write allowlist.** The Modules page and `cli/src/90-main.sh`'s `raw-write)` arm may write ONLY `playerbots.conf`, `mod_ahbot.conf`, `mod_ale.conf`. `.env` and `docker-compose.override.yml` are read-only there — they would let the editor plus a restart drive host command execution. Change those via the curated Settings tab / `config set`. Full context in [`launcher/CLAUDE.md`](launcher/CLAUDE.md).
- **THE MySQL WRITE POLICY, one list (updated 2026-08-03).** MySQL is read-only and mutations go over SOAP GM commands, with exactly FOUR sanctioned write surfaces, each narrow and each behind its own safety: (1) `wow backup restore` — snapshot import, world+auth stopped, automatic `-prerestore` safety dump; (2) the LAN toggle's realmlist `UPDATE`; (3) `account_write.rs` — the SRP6 SOAP-account INSERT (sanctioned 2026-08-01; INSERT-only, refuses an existing name, bound params, proves itself by a live SOAP round-trip); (4) `unbound.rs` — the Wrath Unbound migrations and their uninstall revert (sanctioned 2026-08-02 with the port itself; embedded fingerprint-pinned SQL only, never spliced input, nothing runs before a verified world-inclusive safety dump, both directions behind `--accept-data-changes`); (5) `migrate.rs` — the migration dump restore (Task 10, 2026-08-03), whose safety is a REFUSAL rather than a consent prompt, because consent cannot tell you whether the target holds someone's characters: it asks `information_schema` directly and refuses BOTH a non-empty target (`MIGRATE_TARGET_NOT_EMPTY`) and one that did not answer (`MIGRATE_TARGET_UNKNOWN`) — no `--replace` in v1, since overwriting a live server is `backup restore`'s job and that one takes a safety dump. Anything else that wants to write MySQL is a user decision FIRST, then joins this list.

## Gotchas

- **A detector with ONE signal fails OPEN, and nothing about the output looks broken (2026-08-01, mirrored bash↔Rust).** Every bot-vs-human check asked a single question — is the account in `acore_playerbots.playerbots_account_type` with `account_type IN (1,2)`? mod-playerbots populates that registry ITSELF, and on the freshly built `native-test` install it was **empty** (0 rows; `playerbots_random_bots` and `playerbots_account_links` too) while 1000 bot characters existed on 100 `RNDBOT*` accounts. `account NOT IN (<empty set>)` is TRUE for every row, so Home listed all 1000 bots as real players while "Bots online" read 0 — measured old-vs-new on that live DB: humans 1000→0, bots 0→1000. Bot identity now lives in ONE place per surface (`crates/dml-wow/src/botid.rs`, bash `_bot_prefix`/`_bot_account_where`/`_human_account_where` in `cli/src/30-db.sh`) and takes EITHER signal: registry membership **OR** `acore_auth.account.username LIKE '<AiPlayerbot.RandomBotAccountPrefix>%'` (default `rndbot`, `.conf` → `.conf.dist` → default, env `DML_BOT_ACCOUNT_PREFIX`). Three rules, each load-bearing: an **empty** prefix is refused (it would compile to `LIKE '%'` and call the whole family bots — the mirror-image failure), `%`/`_`/`\`/`'` are escaped so a custom prefix cannot widen the match, and stats' schema-probe failure now degrades to prefix-only instead of `0=1` ("this box has no bots" is a lie on a box that has them). The Home "Players online" NUMBER came from the same incident but has a different cause: SOAP `.server info` "Connected players" counts bot sessions by design, so the number now comes from the bot-free DB list (refetched each poll) and the raw SOAP figure survives only as a labelled "Sessions (incl. bots)" diagnostic row.
- **A Linux container CANNOT run the title installers (proven 2026-08-01, negative result).** A container with the docker socket mounted DOES drive the host daemon - but a nested bind mount silently resolves against the HOST filesystem, so `./modules:/azerothcore/modules` arrives as a path that does not exist there, and **a bind mount to a missing path is not an error, it is an EMPTY DIRECTORY**. The server then boots without its modules and looks healthy to every check we have (the recorded "boots a silently wrong server" class). Passing Windows host paths works, but `docker compose` computes absolute paths from ITS OWN cwd, so the installers would have to be patched - and using them unmodified was the whole appeal. Docker Desktop's WSL integration has none of this, which is why the `.sh` route uses a distro. `docker-desktop` itself has **no bash at all**, so it can never host them.
- **A FIX WITH TWO HALVES IS NOT PROVEN BY A SEQUENCE TEST — the halves mask each other.** The fix had two independent parts: (a) an override that says "allow this", and (b) "and do not spend the budget doing so". The obvious test drove twenty requests through the real guard and asserted none escaped. Deleting half (a) left it **GREEN**: not spending the budget keeps the counter at zero, so the ordinary rule answers yes anyway for as long as you care to iterate. The override was only ever load-bearing where the ordinary rule says NO. A sequence test proves the CONJUNCTION; either half alone satisfies it. When a fix has independent halves, write the case that ISOLATES each one and mutate each half separately — the sequence test is still worth having, it is just not evidence about either part.
- **A test that scans source for a banned string must strip COMMENTS first.** Bit twice on 2026-08-01: `feature-keys.test.ts` parsed a comment containing a lock call as a call site, and `Test-InstallerNative.ps1` read the installer's own explanation of why it never runs `wsl --install`/`pacman` as evidence that it does. Fix: scan the token stream (PowerShell) or require a real call shape - never a raw grep over the whole file.
- **Anchor an ordering test on the REFUSAL, not on "X appears before Y".** `Test-InstallerNative.ps1` compared the first `Get-FileHash` against `Move-Item` to prove a download is verified before install - vacuous, because the function opens with an unrelated hash check, so the exact mutation it existed to catch stayed green. The invariant that holds is `throw` before `Move-Item`.

- **Line endings:** bash inside WSL chokes on CRLF. `.gitattributes` forces LF for `*.sh`, `*.bats`, `*.bash`, and `cli/dml`; keep new shell files LF.
- **PowerShell 5.1 + UTF-8:** BOM-less `.ps1` files containing non-ASCII (em dashes) mis-parse under the ANSI codepage. `cli/tests/windows-smoke.ps1` carries a UTF-8 BOM on purpose; keep BOMs on any non-ASCII `.ps1`.
- **Rust toolchain PATH:** Rust 1.97 MSVC is installed per-user but `%USERPROFILE%\.cargo\bin` may be missing from a fresh Claude shell's PATH — use the full path or prepend it per call. MSVC Build Tools 2022 (C++ workload) and Node 22 are installed; WebView2 present.
- **`bats tests/ | tail -40` reports the exit code of `tail`, always 0.** Cost a false "all 826 pass" on 2026-08-01: the tail happened to end on passing tests while `wow-stats.bats` was red the whole time. Redirect to a file and read the code (`bats tests/ > out 2>&1; echo $?`), then `grep -c '^not ok' out` — never judge a bats run by a piped tail. Same trap for any `cmd | tail`/`| Select-String` in PowerShell.
- **`bats` and `jq` are NOT on the Git Bash PATH on this machine — they live inside the WSL distro.** Running `bats cli/tests/` from a Windows Git Bash shell produces **92 failures, 89 of them `jq: command not found`** — a red suite that is measuring the shell, not the code, and reads exactly like a real regression. Run it in the distro instead: `wsl -d dml-arch -u dml -- bash -lc 'cd /mnt/c/Users/perzi/dads-mmo-lab && bats cli/tests/ > /tmp/bats.out 2>&1; echo EXIT=$?'`, then read the counts out of `/tmp/bats.out` in a SEPARATE call (see the piped-tail trap directly above).
- **NEVER run bats and the cargo parity suites at the same time:** every bats `setup()` runs `bash cli/build.sh`, which REWRITES `cli/dml` in place, while the Rust parity suites spawn `bash cli/dml` as their oracle. Overlap makes bash read a half-written file and fail with `cli/dml: line NNNN: syntax error: unexpected end of file` — a red suite that looks like a real regression and is not (hit 2026-07-28 during the round-2 merge gate). Run them sequentially.
- **A test-double whose "override" is silently ignored is a vacuous-pass generator.** Two instances found the same day (2026-07-29), both in harnesses that looked obviously correct: (1) `install_native.rs`'s `FakeIo` registered scripted answers by pushing onto a `Vec` and resolved them with a FIRST-match scan, so every reply a test registered after the shared `happy_io()` builder was unreachable — 7 tests were asserting against `happy_io`'s answers and reported the ENGINE as broken when the engine was fine. Fixed by replacing same-key entries in place (`FakeIo::set`). (2) `cli/tests/helpers/env.bash`'s tailscale stub used `${DML_STUB_TS_UP_URL:-<default>}`, and `:-` substitutes the default for an EMPTY value too — so a test that set it empty to mean "printed no URL" still got a real URL, and the test proved nothing. Use `${VAR-default}` when empty must be honoured. Rule: after writing a test that overrides a shared fixture, MUTATE the production code and watch it go red — an override you never proved took effect probably didn't.
- **Build memory:** `.cargo/config.toml` pins `build.jobs = 8` and the root `Cargo.toml` sets `[profile.dev] debug = "line-tables-only"` (deps: none). Uncapped, cargo fans out to the logical CPU count (32 here) and each `link.exe` holds 0.5–1.2 GB, pinning RAM at 100% on a 31 GB box that also reserves 16 GB for WSL2. Don't run `cargo run` (tauri dev) and `cargo test --workspace` at the same time — same `target/` lock, double the peak. Changing either setting forces one full rebuild.
- **`wsl.exe --` RUNS A SHELL; `--exec` does not.** Verified 2026-07-28: `wsl -d dml-arch -u dml -- printf '[%s]\n' 'a;whoami' 'b$HOME' '*'` split on the `;`, expanded `$HOME` and globbed `*` against the cwd; the same call with `--exec` printed all three back verbatim (spaces survive either way, so the bug hides until a path carries a metacharacter). The production spawn `wsl.exe -d dml-arch -u dml -- dml <cmd> --json` and the `dml_core::setup` probe chain deliberately keep `--` (that is the documented contract, and their args are our own literals). Anything passing a HOST path or user text through wsl.exe must use `--exec` and real argv — see `launcher/src-tauri/src/provision.rs`, where sources come from wherever the user installed the launcher.
- **Windows→distro path translation: ask `wslpath`, never do string surgery.** `C:\x` → `/mnt/c/x` only holds for the default automount root (`/etc/wsl.conf` can move it) and has no UNC form at all. `provision.rs` translates the resource dir once via `wsl --exec wslpath -a -u` and joins every source onto the answer.
- The `games` namespace is JSON-first: `games list`/`status` always emit JSON; only `games start|stop|restart` have a text mode. Legacy top-level commands (`list`, `status`, `start`, …) keep their exact text output — the old C# tray parses it.
- `dml-start.sh` hook: `games start|restart` run `<compose_dir>/dml-start.sh <mode>` when present+executable (avoids re-running ac-db-import on restarts).
