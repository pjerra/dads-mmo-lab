- Root `Cargo.toml` is the workspace; members are `crates/dml-core`, `crates/dml-wow`, `crates/dml-wow-cli`, `launcher/src-tauri`. `Cargo.lock` lives at the repo root, and so does `target/`.

Config/tuning/module registries are `include_str!`-embedded from `crates/dml-wow/data/` (config 66 rows, tuning 13, catalog cpp 19 / lua 9 / sql 10), so the native path no longer shells the bash CLI for them — regenerate them from the bash oracle if `cli/` changes.

- **`install_native.rs` — the Route A native install engine (2026-07-29).** Staged, RESUMABLE state machine that turns an empty title dir into a running stack on Docker Desktop with no WSL distro: `preflight → guard → clone-core → clone-module → generate-compose → build → up → ready`, streamed as NDJSON. CLI surface is `dml-wow install-native [--id X] [--allow-underspec]` (distinct from `install`, which stays the interactive WSL passthrough; native-only BY DESIGN — bash's `_installers_supported` refuses on Windows, so there is no bash mirror). Resume rests on TWO things only: `.dml-install.json` in the title dir (written ONLY after a stage really finished, and bound to that dir by `composegen::install_id`, so a copied state file is refused) and Docker's BuildKit cache. `preflight`/`guard` are deliberately never recorded — a guard a resume skips is not a guard. Two refusals matter: `INSTALL_COMPOSE_EXISTS` (never generate over a compose file DML did not write — the default games dir `%USERPROFILE%\dml-native` IS the working migrated server) and `INSTALL_STACK_CONFLICT` (the `ac-*` `container_name`s are global to the docker ENGINE, so one stack per PC; per-install names are a recorded follow-up). Contract documented in `docs/cli-contract.md`. **Launcher wiring is NOT done** — reachable only by running the binary today.
- **`soap_bootstrap.rs` - the guided post-install account step (2026-08-01).** A fresh AzerothCore has NO accounts, so until one exists at GM3 every SOAP feature (GM Tools, My Party, console send, announcements) fails with a bare `SOAP_AUTH`. GUIDED, not automated, and the reason was tested rather than assumed: **`docker attach` REFUSES piped stdin against a TTY container** ("stdin is not a terminal") and the worldserver runs `stdin_open: true` + `tty: true`; dropping the tty does not rescue it either - attach then accepts the pipe and NEVER RETURNS. The only other route is an SRP6 `INSERT` into `acore_auth`, which would be a THIRD sanctioned MySQL write and stays an open user decision. What the module guarantees is that **"done" is earned**: `~/.dml/soap.env` is written ONLY after a real round-trip. `Rejected` and `Unreachable` are separate outcomes - the usual cause of unreachable is a world server still booting, and blaming the password sends the user to recreate a working account.
- **The port-conflict REFUSAL (2026-08-01, mirrored bash-Rust).** `lifecycle::stack_port_refusal` + `STACK_PORTS` (3724/8085/7878 only - the ports this stack publishes) refuses a cold `start`; the 17-port `CONFLICT_PORTS` sweep stays advisory. **3306 is deliberately excluded**: it is the one collision with a real automatic remedy (the `.env` `DOCKER_DB_EXTERNAL_PORT` remap). Uses the NEW `dml_core::compose::port_probe -> Tri`, not `port_listening -> bool`: the latter reads ANY bind failure as "in use", which is right for a warning and would turn a `PermissionDenied` or a Hyper-V-reserved port range into a refusal to start a server that works.
- **The `pct` event is live (2026-08-01), and it is the ONE number in this repo that is not a guess.** `{"event":"pct","value":62}`, advisory, no stage name (the consumer reads the stage from the enclosing `section_start`). Emitted by exactly one place: `install_native.rs`'s `build` stage, parsed from **ninja**'s `[1803/1808]` counter in the streamed docker output (AzerothCore's Dockerfile installs `ninja-build`, so the denominator is real and known). Three rules, each from a real build log, and all three are load-bearing: the bracket must be **digits-only** (BuildKit's vertex header carries a Dockerfile-stage `2/4` that would slam the bar to 50% during a 0.1s `mkdir`), the **largest-total vertex wins** (four images build in parallel; a 3-step sidecar must not outbid the 1808-step compile), and the number **never goes down**. Emitted only on change, so a 1808-step build produces ≤101 events. Frontend: `launcher/src/lib/install-progress.svelte.ts` (module-level runes store + pure reducer, mirrors `restart-state.svelte.ts` so it survives navigation) feeding `statusLabel`, whose precedence is now **installing > restarting > polled verdict**. `install` is a REQUIRED third parameter there on purpose — an optional one lets a call site quietly go back to reporting a compiling machine as an idle server. NB Home's status card does not share the chip's markup: its install branch sits **above** the `{#if serverStatus.detail}` gate, because on a first install `server-detail` errors (no compose file yet) and the card otherwise falls through to "Couldn't read world status" for the whole build. Spec: `docs/superpowers/specs/2026-08-01-install-progress-status-design.md`.
- **Contract docs (keep in sync when the CLI surface changes): `docs/cli-contract.md`** (envelopes, NDJSON vocabulary, exit codes, full command table, env vars, caveats) and `docs/rust-cli-pitch.md`.

- **Test-portability rules, learned the hard way:** never hardcode `cmd.exe` or a drive-letter `Path` literal in a test — use a per-platform `#[cfg]` helper (the convention lives in `dml-core`'s `runner.rs`/`proc.rs` and `dml-wow`'s `backup.rs`/`restore.rs`). `std::env::join_paths` rejects a component containing the platform's PATH separator, so `C:\...` entries fail on Unix. Forward-slash path literals work on BOTH flavours; backslash ones are Windows-only.
- **The vacuous-pass trap:** `cargo test` captures `eprintln!` from PASSING tests, so a suite that skips for a BROKEN reason looks identical to one that ran. That is why the Linux CI job runs with `-- --nocapture`, and why every parity suite's `find_bash`/`yq_path` gate is per-platform. When a test's assertion could be satisfied by an early error return, assert something a failed spawn cannot satisfy (e.g. elapsed >= the deadline). **Its sibling: never pin an ordering invariant on a pure list that production never reads** — `lifecycle_steps_for_mode` restated the pre-stop order (`logsnap` → `backup` → `down`) and its 4 tests stayed green when the real snapshot call was moved or deleted. Deleted; the order is now asserted against the real call site (`games_lifecycle_stream_with`, driven via `LifecycleEnv` + a fake `docker` whose calls are read back in order — the same oracle `cli/tests/games-log-snapshot.bats` uses).
- **List order is NOT contractual:** bash `sort(1)` collates per locale (en_US = case-insensitive), Rust `Vec::sort` is byte order. Compare file sets, not positions.

Frontend copy lives in `launcher/src/lib/title-install.ts` (pure, vitest-pinned) — one hint per reason plus a page notice; `normalizeCatalog` FAILS OPEN on a missing `install_supported` so an older `dml` in dml-arch keeps working. `games catalog` has no Rust mirror, so this is a bash-only surface.
- **Tailscale login (fixed 2026-07-29, mirrored bash↔Rust):** `tailscale up`'s wait defaults to **45s** via `DML_TS_UP_TIMEOUT` — measured, not guessed: on a clean VM the control plane took 30s to return the auth URL while the old hardcoded 8s gave up at 8, so the user got a bare "timeout waiting for Tailscale service to enter a Running state" and never received the URL that would have let them finish the login by hand. Three rules now hold on BOTH surfaces: the outer process bound must outlive the inner `--timeout` (`TS_UP_OUTER_SLACK_SECS`; raising only the inner one lets our own kill land first), a missing URL is retried by reading `AuthURL` back out of `tailscale status --json` (the daemon keeps the pending URL after `up` gives up — grep, never jq, which is test-only here), and the daemon-start step's failure is REPORTED (`TAILSCALE_DAEMON_FAILED` / `SUDO_REQUIRED`) instead of discarded — previously a sudo refusal, a missing unit, a dying daemon and a merely-slow one all produced the identical useless message.
- Sanitization invariants (tested; keep them): `_xml_escape` escapes `&` FIRST; `sql_escape` escapes `\` then `'`; SOAP-bound free text strips `"`/CR/LF (AC #2695 second-command surface); numeric values are `^[0-9]+$`-whitelisted before SQL splice; every value-taking flag calls `_need_flag_val` before reading `$2` (else `set -u` aborts with no JSON envelope).
- bash while-read loops fed from command substitution need `|| [[ -n "$var" ]]` (trailing-newline strip silently drops the last row otherwise) — see `_items_rows_to_json`.

## Gotchas

- **A Linux container CANNOT run the title installers (proven 2026-08-01, negative result).** A container with the docker socket mounted DOES drive the host daemon - but a nested bind mount silently resolves against the HOST filesystem, so `./modules:/azerothcore/modules` arrives as a path that does not exist there, and **a bind mount to a missing path is not an error, it is an EMPTY DIRECTORY**. The server then boots without its modules and looks healthy to every check we have (the recorded "boots a silently wrong server" class). Passing Windows host paths works, but `docker compose` computes absolute paths from ITS OWN cwd, so the installers would have to be patched - and using them unmodified was the whole appeal. Docker Desktop's WSL integration has none of this, which is why the `.sh` route uses a distro. `docker-desktop` itself has **no bash at all**, so it can never host them.
- **A test that scans source for a banned string must strip COMMENTS first.** Bit twice on 2026-08-01: `feature-keys.test.ts` parsed a comment containing a lock call as a call site, and `Test-InstallerNative.ps1` read the installer's own explanation of why it never runs `wsl --install`/`pacman` as evidence that it does. Fix: scan the token stream (PowerShell) or require a real call shape - never a raw grep over the whole file.
- **Anchor an ordering test on the REFUSAL, not on "X appears before Y".** `Test-InstallerNative.ps1` compared the first `Get-FileHash` against `Move-Item` to prove a download is verified before install - vacuous, because the function opens with an unrelated hash check, so the exact mutation it existed to catch stayed green. The invariant that holds is `throw` before `Move-Item`.

- **Line endings:** bash inside WSL chokes on CRLF. `.gitattributes` forces LF for `*.sh`, `*.bats`, `*.bash`, and `cli/dml`; keep new shell files LF.
- **PowerShell 5.1 + UTF-8:** BOM-less `.ps1` files containing non-ASCII (em dashes) mis-parse under the ANSI codepage. `cli/tests/windows-smoke.ps1` carries a UTF-8 BOM on purpose; keep BOMs on any non-ASCII `.ps1`.
- **Rust toolchain PATH:** Rust 1.97 MSVC is installed per-user but `%USERPROFILE%\.cargo\bin` may be missing from a fresh Claude shell's PATH — use the full path or prepend it per call. MSVC Build Tools 2022 (C++ workload) and Node 22 are installed; WebView2 present.
- **NEVER run bats and the cargo parity suites at the same time:** every bats `setup()` runs `bash cli/build.sh`, which REWRITES `cli/dml` in place, while the Rust parity suites spawn `bash cli/dml` as their oracle. Overlap makes bash read a half-written file and fail with `cli/dml: line NNNN: syntax error: unexpected end of file` — a red suite that looks like a real regression and is not (hit 2026-07-28 during the round-2 merge gate). Run them sequentially.
- **A test-double whose "override" is silently ignored is a vacuous-pass generator.** Two instances found the same day (2026-07-29), both in harnesses that looked obviously correct: (1) `install_native.rs`'s `FakeIo` registered scripted answers by pushing onto a `Vec` and resolved them with a FIRST-match scan, so every reply a test registered after the shared `happy_io()` builder was unreachable — 7 tests were asserting against `happy_io`'s answers and reported the ENGINE as broken when the engine was fine. Fixed by replacing same-key entries in place (`FakeIo::set`). (2) `cli/tests/helpers/env.bash`'s tailscale stub used `${DML_STUB_TS_UP_URL:-<default>}`, and `:-` substitutes the default for an EMPTY value too — so a test that set it empty to mean "printed no URL" still got a real URL, and the test proved nothing. Use `${VAR-default}` when empty must be honoured. Rule: after writing a test that overrides a shared fixture, MUTATE the production code and watch it go red — an override you never proved took effect probably didn't.
- **Build memory:** `.cargo/config.toml` pins `build.jobs = 8` and the root `Cargo.toml` sets `[profile.dev] debug = "line-tables-only"` (deps: none). Uncapped, cargo fans out to the logical CPU count (32 here) and each `link.exe` holds 0.5–1.2 GB, pinning RAM at 100% on a 31 GB box that also reserves 16 GB for WSL2. Don't run `cargo run` (tauri dev) and `cargo test --workspace` at the same time — same `target/` lock, double the peak. Changing either setting forces one full rebuild.
- **`wsl.exe --` RUNS A SHELL; `--exec` does not.** Verified 2026-07-28: `wsl -d dml-arch -u dml -- printf '[%s]\n' 'a;whoami' 'b$HOME' '*'` split on the `;`, expanded `$HOME` and globbed `*` against the cwd; the same call with `--exec` printed all three back verbatim (spaces survive either way, so the bug hides until a path carries a metacharacter). The production spawn `wsl.exe -d dml-arch -u dml -- dml <cmd> --json` and the `dml_core::setup` probe chain deliberately keep `--` (that is the documented contract, and their args are our own literals). Anything passing a HOST path or user text through wsl.exe must use `--exec` and real argv — see `launcher/src-tauri/src/provision.rs`, where sources come from wherever the user installed the launcher.
- **Windows→distro path translation: ask `wslpath`, never do string surgery.** `C:\x` → `/mnt/c/x` only holds for the default automount root (`/etc/wsl.conf` can move it) and has no UNC form at all. `provision.rs` translates the resource dir once via `wsl --exec wslpath -a -u` and joins every source onto the answer.
- The `games` namespace is JSON-first: `games list`/`status` always emit JSON; only `games start|stop|restart` have a text mode. Legacy top-level commands (`list`, `status`, `start`, …) keep their exact text output — the old C# tray parses it.
- `dml-start.sh` hook: `games start|restart` run `<compose_dir>/dml-start.sh <mode>` when present+executable (avoids re-running ac-db-import on restarts).
