- **Incident follow-ups (2026-07-28), both mirrored bash↔Rust — a fix on one surface only half-ships:** (1) `games stop|restart` snapshot a bounded tail of the worldserver log to `~/.dml/logs/world-<UTC ts>-<title>-<mode>.log` BEFORE the compose down that recreates the container and destroys its log (`_snapshot_world_log` in `cli/src/90-main.sh`, `crates/dml-wow/src/logsnap.rs`; best-effort, newest-`DML_LOG_SNAPSHOT_KEEP` retention, timestamp leads the file name so a plain name sort is chronological). The container is resolved through the STOPPING title's own compose project (`compose ps -a -q ac-worldserver` in its compose dir) — a bare `docker logs ac-worldserver` answers for whichever title owns it, so a non-WoW title's stop used to file the WoW log under its name and evict the real evidence; both docker calls are time-bounded (`DML_LOG_SNAPSHOT_TIMEOUT`, default 20s), the prune never touches the file just written (and `KEEP=0` = off) so a reported name always exists, and prunes are SILENT on both surfaces (line set: `logsnap::snapshot_lines`). (2) BOOT-LOOP DIAGNOSIS on `.State.RestartCount` climbing by 3 since the wait began, emitting one latched `warn` line naming the cause + the Restart Docker action — advisory only, the outcome/exit code never change. ONE tracker per surface drives BOTH call sites (`_boot_loop_reset`/`_boot_loop_check`/`_boot_loop_note` in `cli/src/40-config.sh`, `BootLoopWatch`/`boot_loop_note` in `crates/dml-wow/src/lifecycle.rs`): the `world-restart` wait, AND — the path Home's Start/Restart buttons actually take — `_stream_cmd_bootwatch`, which wraps the `dml-start.sh` hook and ticks on its OWN `read -t` clock so a silent hook is still diagnosed. NB the repo's `guides/wow-wotlk/dml-start.sh` is deliberately NOT the host: it is deployed into each title dir at install time, so editing it would only ever reach FRESH installs — the watch lives in `cli/dml` (which existing installs do get updated) and watches the deployed hook from the outside. Native mode arms the same watch, but `docker compose up -d` returns in seconds and there is no native readiness wait for it to span, so its practical reach is thin — the honest gap there is the MISSING native readiness wait, not the detection. Both reuse the tri-state lesson: docker failing to answer is evidence of NOTHING.
- **Title installs are WSL-ONLY (2026-07-28 blocker fix):** all six installers under `guides/*/install-*.sh` are Linux scripts (`sudo -v`, pacman/apt, `systemctl`, `usermod -aG docker`, `/etc/sudoers.d`, `chmod /var/run/docker.sock`), so they cannot run under Git Bash on Windows — native mode CANNOT install a title, and no amount of path resolution changes that. `_installers_dir` defaults to `/usr/local/share/dml/installers`, which simply does not exist on a Windows host, so `games catalog` reported `script_available:false` for every title and the Library page told everyone to "re-run cli/dev-install.ps1" — a step that was already fine. The two questions are now separate: `script_available` stays a pure file-existence answer, and `games catalog` also emits **`install_supported`** (`_installers_supported` → `_host_bash_is_windows` in `cli/src/00-head.sh`, which `doctor`'s `_host_is_native_windows` now shares; seam `DML_OSTYPE`). `games install` checks the host BEFORE the file so it never blames dev-install either. Frontend copy lives in `launcher/src/lib/title-install.ts` (pure, vitest-pinned) — one hint per reason plus a page notice; `normalizeCatalog` FAILS OPEN on a missing `install_supported` so an older `dml` in dml-arch keeps working. `games catalog` has no Rust mirror, so this is a bash-only surface.
- **Tailscale login (fixed 2026-07-29, mirrored bash↔Rust):** `tailscale up`'s wait defaults to **45s** via `DML_TS_UP_TIMEOUT` — measured, not guessed: on a clean VM the control plane took 30s to return the auth URL while the old hardcoded 8s gave up at 8, so the user got a bare "timeout waiting for Tailscale service to enter a Running state" and never received the URL that would have let them finish the login by hand. Three rules now hold on BOTH surfaces: the outer process bound must outlive the inner `--timeout` (`TS_UP_OUTER_SLACK_SECS`; raising only the inner one lets our own kill land first), a missing URL is retried by reading `AuthURL` back out of `tailscale status --json` (the daemon keeps the pending URL after `up` gives up — grep, never jq, which is test-only here), and the daemon-start step's failure is REPORTED (`TAILSCALE_DAEMON_FAILED` / `SUDO_REQUIRED`) instead of discarded — previously a sudo refusal, a missing unit, a dying daemon and a merely-slow one all produced the identical useless message.
- **Schema-name divergence CLOSED for user-data surfaces (2026-08-07, Task 6 chunk B1; opened 2026-08-06).** bash now mirrors Rust's resolution: `_db_names_resolve` in `30-db.sh` (memoized per invocation) resolves `acore_world`/`acore_characters`/`acore_auth` + the OPTIONAL playerbots schema from the server's own config — compose `AC_*_DATABASE_INFO` env (`docker-compose.override.yml`, then the base compose, read by a pure-awk service-scoped extractor handling both the mapping and `- KEY=value` list forms; **no yq on the DB path**) → `worldserver.conf` `*DatabaseInfo` → its `.dist`; parse mirrors `parse_database_info` byte-for-byte (trim, strip quotes, ≥4 semicolons, LAST field, `[A-Za-z0-9_$]` charset, all-digits refused). Unresolvable core trio ⇒ `json_err DB_NAMES_UNRESOLVED` (`_db_names_require` at each DB-verb arm; streaming arms `_db_names_require_stream`) BEFORE any docker exec — never a guessed default, never mislabelled `DB_UNREACHABLE`. `_db_write_stmt`'s allowlist is **re-anchored on the resolved trio** — still a closed set of three plus a charset re-check, never widened. Playerbots absent ⇒ prefix-only bot SQL and a dump set that omits the schema **with a narrated warn** (the copy mirrors `backup.rs::dump_narration` byte-for-byte). Proof lives in `cli/tests/wow-db-names.bats` (renamed-server end-to-end, list-form compose, tier precedence, refusal-before-docker, truncated/hostile/all-digits values, the re-anchored allowlist, the playerbots omission + narration) — no parity suite compares SQL text/argv, so those tests ARE the mirror's evidence. **Recorded exceptions, still hardcoded with reasons at each site:** the module subsystem (`70-modules.sh` `_ale_sql_file`/`_sqlmod_run_*`, `90-main.sh` module sql/repair/fixit/place-npc incl. `db_full="acore_$rdb"`; module SQL payloads hardcode standard names internally — on a renamed server they now refuse at the re-anchored allowlist, the honest outcome; `acore_ale` is module-owned) and legacy text-mode `lan` (frozen output contract, spans server families; Rust's lan path resolves via `Database::Auth`). `config list`'s motd read keeps its degrade-to-registry-default (refusal is for fabricated answers, not paths that already handle absence), as do `server-detail`'s `_bots_counts`, the backup summary sidecar, and `wow item-info`'s local lookup (`46-iteminfo.sh` — DB failure already degrades to `source:"unavailable"`, same as DB-down). **Two known extractor caveats, found by the B1 review (fixture-proven, both exotic-but-legal YAML):** (1) a FLOW-style `environment: { AC_…: … }` is invisible to the awk extractor, so bash falls to the conf tier while Rust resolves the flow map — on a native-shaped install with a stock conf that is the wrong-source bug on that one compose shape; (2) an `environment:` mapping nested DEEPER inside the ac-worldserver block (e.g. under `build:`) is read by bash but correctly ignored by Rust. Both only matter on hand-rewritten or tool-round-tripped composes; DML never generates either shape. Closing them means teaching awk real YAML — record here, revisit only if a real compose ever hits it.
- **`_module_can_build` mirrors Rust's `cpp_build_guard`/`buildcap` (2026-08-09).** A tri-state `docker compose config` probe, scoped to the same `-f` set (`docker-compose.yml` + override + `docker-compose.build.yml`): `yes`/`no` are authoritative, `unknown` (docker down or unparseable config) is NOT a refusal — it warns and proceeds, same fail-open rule as every other tri-state probe in this repo. `no` refuses `module install --family cpp`, a cpp-shaped `module update`, and `module rebuild` with `MODULE_NO_BUILD_CONFIG` (before cloning/pulling/backing up); `module list`'s `.data` also carries `can_build`, reusing this same probe collapsed to a bool (`true` for `yes`/`unknown`, `false` only for a definite `no` — the UI's disable signal fails open too; the Rust native reader answers the same field from plain disk evidence instead, `docker-compose.build.yml` present or not — see `docs/cli-contract.md`). **bash's `module rebuild` (`90-main.sh:5826-5874`) deliberately KEEPS `docker compose up -d --build`** as its build command — only the pre-backup guard was added here, the build step itself is unchanged, because WSL-shaped servers carry `build:` inline in the base compose (proven by the Jul 20 rebuild.log) and have no separate build overlay to miss. The explicit-overlay-then-plain-`up -d` restructure (spec `docs/superpowers/specs/2026-08-09-module-rebuild-fix-design.md` section 2) is Rust-only, because only composegen-generated native servers can carry a `docker-compose.build.yml` overlay for a bare `up -d --build` to silently skip.
