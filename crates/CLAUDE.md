- **`install_native.rs` — the Route A native install engine (2026-07-29).** Staged, RESUMABLE state machine that turns an empty title dir into a running stack on Docker Desktop with no WSL distro: `preflight → guard → clone-core → clone-module → generate-compose → build → up → ready`, streamed as NDJSON. CLI surface is `dml-wow install-native [--id X] [--allow-underspec]` (distinct from `install`, which stays the interactive WSL passthrough; native-only BY DESIGN — bash's `_installers_supported` refuses on Windows, so there is no bash mirror). Resume rests on TWO things only: `.dml-install.json` in the title dir (written ONLY after a stage really finished, and bound to that dir by `composegen::install_id`, so a copied state file is refused) and Docker's BuildKit cache. `preflight`/`guard` are deliberately never recorded — a guard a resume skips is not a guard. Two refusals matter: `INSTALL_COMPOSE_EXISTS` (never generate over a compose file DML did not write — the default games dir `%USERPROFILE%\dml-native` IS the working migrated server) and `INSTALL_STACK_CONFLICT` (the `ac-*` `container_name`s are global to the docker ENGINE, so one stack per PC; per-install names are a recorded follow-up). Contract documented in `docs/cli-contract.md`. **Launcher wiring is NOT done** — reachable only by running the binary today.
- **`soap_bootstrap.rs` - the guided post-install account step (2026-08-01).** A fresh AzerothCore has NO accounts, so until one exists at GM3 every SOAP feature (GM Tools, My Party, console send, announcements) fails with a bare `SOAP_AUTH`. GUIDED, not automated, and the reason was tested rather than assumed: **`docker attach` REFUSES piped stdin against a TTY container** ("stdin is not a terminal") and the worldserver runs `stdin_open: true` + `tty: true`; dropping the tty does not rescue it either - attach then accepts the pipe and NEVER RETURNS. The SRP6 route was then SANCTIONED and built the same day (`srp6.rs` + `account_write.rs`, proven by creating a live account and authenticating over real SOAP): the card's primary action creates the account by writing salt+verifier; the console route stays as the fallback and opens itself on a refusal. What the module guarantees is that **"done" is earned**: `~/.dml/soap.env` is written ONLY after a real round-trip. `Rejected` and `Unreachable` are separate outcomes - the usual cause of unreachable is a world server still booting, and blaming the password sends the user to recreate a working account.
- **`soap_autosetup.rs` — the launcher sets up its own SOAP access (2026-08-01, + two fix waves).** Turns the card above into the FALLBACK: on any status poll where SOAP is reachable and REJECTING us (never on `Unreachable` — a world server still booting is not a broken account), the launcher generates a password, creates `dmlsoap` at GM3 via `account_write` (`dmlsoap_<6 hex>` if taken — never a reset of a row it did not write), proves it over a real SOAP round-trip and raises a shell-level banner naming the account; Home's health panel reveals the password on demand, opt-in at the IPC boundary because a secret that always crosses it is a secret in every devtools trace. The password is **16** chars because `valid_account_pass` caps there and `create_gm_account` runs it FIRST — a "stronger" 32 would earn a `BAD_ARG` on every fresh install, at the one moment the user has nothing to retype. **Rejection sampling, never `byte % 70`** (256 = 3×70 + 46, so modulo gives the first 46 symbols a fourth chance) — and the FIRST test written for it was VACUOUS: the obvious `210..=255` feed proves nothing, because `210 == 3*70` aliases those bytes onto indices 0..=15, character for character the prefix the test asserts, so deleting the discard guard left it green (the feed is 46 copies of `255`, `255 % 70 == 45`, for exactly that reason). `Pending` is why this is a state machine: a create that succeeded followed by a verify that failed must re-verify, never re-create, or the poll writes one GM3 row per tick forever. The `family_taken` seam (`account_family_exists`, `LIKE 'DMLSOAP\_%'`) is the ONLY bound on the account count — the code first asked about the freshly minted `dmlsoap_<hex>`, which is free BY CONSTRUCTION and therefore not a guard at all, and with `DML_SOAP_USER`/`DML_SOAP_PASS` exported (they outrank the `soap.env` this writes, so SOAP keeps reading `Rejected`) every launcher start minted one more GM3 account, unbounded. **There is no contentless "already done" answer**: `AutoOutcome::Latched` and the `"latched"` wire literal are DELETED, and a concluded run re-derives its real verdict through `concluded_outcome()` — the frontend's memory of the run is a module-level store that a webview reload wipes, so a reloaded UI told only "already concluded" never rendered the manual card again, on the exact path where setup had FAILED and the card was the only thing left that worked. The latch is per launcher RUN: a mid-session auth wipe needs a relaunch to self-heal, which beats an unlatched loop writing rows into a database that keeps losing them. `Library.svelte` carries NO SOAP surface any more (a fallback reachable from one page is the same bug this removes) — pinned by `launcher/src/lib/soap-surface.test.ts`, which `code()`-strips comments before matching, because that file is dense with `// … soap …` prose a raw grep reads as a live call site. **No bash mirror**, like `srp6.rs`/`account_write.rs`. - **TWO BOUNDED-CALL FIXES LANDED HERE BY PORT, and in both the failure looked like a working system.** (1) `dml_core::proc::run_bounded_outcome` killed its child at the deadline and then JOINED the two reader threads, on the stated grounds that killing the child closes its pipes. It does NOT, when the child spawned a GRANDCHILD that inherited the handles: measured, a 600ms-bounded call against `cmd /C ping -n 600` returned after **605 SECONDS**. `docker`, `wsl.exe` and `git` all spawn helpers, so this was every bounded probe in the project quietly losing its bound. Both paths are bounded now against ONE clock — `bounded_outcome_after_spawn` derives `deadline` once, the timeout path calls `abandon` (kill, then reap on a thread nobody waits for: `kill()` can fail and the `wait()` that followed it was infinite for a process whose whole problem is that it outlives the deadline), and the success path drains through `BoundedReader::collect_by(deadline)`, returning `TimedOut` rather than a truncated `Ran`. That choice is load-bearing: `Ran` is the shape every caller reads as "here is the answer", so a half-read distro list under `Ran { code: Some(0) }` is not a smaller answer, it is a WRONG one, and `TimedOut` reaches the probe layer as the honest `ProbeOutcome::CouldNotTell`. The invariant is the WIRING, not either half — replacing both `collect_by` arguments with a fabricated `Instant::now() + 3600s` left all 154 `proc::`/`setup::`/`engine::` tests green — so the pin (`the_drain_is_bounded_by_the_same_clock_the_poll_loop_used`) brackets elapsed time from BOTH sides, and the readers are generic over `std::io::Read` so a fake whose `read` blocks reproduces "child gone, grandchild holding the pipes" deterministically, where a real grandchild is a wall-clock race that passes with the bug reinstated. (2) `engine::ensure_decision` took a collapsed `bool`, so a MISSING docker CLI was indistinguishable from a merely-stopped engine — it launched Docker Desktop and then polled `docker info` through the CLI that does not exist, 61 times, 3s apart. Now `EnginePresence{Up,Down,CliMissing}` + `engine_presence`, and `EnsureDecision::NoDockerCli` **OUTRANKS** `desktop_found`, because the readiness probe runs THROUGH the CLI. `CouldNotTell` still reads as `Down` on purpose — a probe that blew its deadline is evidence of nothing, and promoting it would refuse to start an engine that was merely slow. Same round: `engine::start_engine` (`docker desktop start -d`) had **no** wall-clock bound at all — the one command reached specifically because the engine is not answering — now `ENGINE_START_ASK_TIMEOUT` (60s), with a timeout reading as the existing "fall back to the exe".

- **A MOVING IMAGE TAG SILENTLY REPLACED THE USER'S SERVER (live incident, 2026-08-02).** The migration saves the user's OWN built images (`docker save`) and they carry upstream's own tag, `acore/ac-wotlk-<svc>:master`, because that is what the WSL server ran under. Weeks later an ordinary `docker compose up` pulled a fresher `:master` and **overwrote all four** with stock AzerothCore. Three symptoms, one cause, and nothing in the output named it: **bots did not load** (playerbots was no longer IN the binary — not a config problem), the worldserver logged `mmtile was built with generator v19, expected v20` (upstream's newer build wants newer client data), and `ac-client-data-init` exited 1 trying to fetch v20 — which it could never do, because the volume is root-owned while the container runs as uid 1000, a latent flaw the version bump exposed. Recovery was the user's own `img-*.tar.gz` in the server dir. **The fix, both for that server and in `poc/native-docker/migrate/`: run migrated stacks from `dml.local/ac-wotlk-<svc>:${DML_LOCAL_TAG:-migrated}`**, a namespace no registry serves — a missing image is then a loud `pull access denied` instead of a silent substitution. `check-migrate-scripts.sh` asserts both directions (mutation-proven). **Diagnostic lesson worth as much as the fix:** the first check ran `strings worldserver | grep -c playerbot` and reported 0 — but `strings` is ABSENT from the image, so the `|| echo 0` fallback made "no playerbots" and "no strings binary" indistinguishable. Grepping the binary directly gave 3388, and `worldserver --version` said `(Playerbot branch)` outright. A probe whose failure mode looks exactly like its negative answer is not a probe.
- **THE STACK-CONFLICT GUARD, and the two live bugs it caused (2026-08-02, mirrored bash↔Rust).** The refusal asks the only honest question — do the engine-global `ac-*` container names belong to someone else — but "someone else" was decided by the DERIVED compose project name, and that was wrong twice on real machines. (1) The user's migrated server runs under the project `dml-wow-native`, a migration-era name `composegen::project_name_for` can never produce, so the launcher refused to start **their own server** and told them to go stop it. (2) The bash side compared paths BYTE-wise while Git Bash spells `$PWD` as `/c/Users/...` and the compose label spells it `C:\Users\...`. "Ours" now holds on EITHER signal: the derived name matches, OR `com.docker.compose.project.working_dir` names the directory we are about to compose from — ground truth that survives `COMPOSE_PROJECT_NAME` and top-level `name:`. The ps format is TAB-separated (working dirs hold spaces) and `canon_path`/`_canon_path` fold the four spellings of one directory (`C:\x`, `C:/x`, `/c/x`, `/mnt/c/x`), lowercasing only drive-rooted paths — on Linux `/srv/A` and `/srv/a` really differ. Bash deliberately does NOT use `realpath`: Git Bash's mangles `C:\` into cwd-relative nonsense. Three more rules from the same round: the guard runs on **restart too** (the start-only gate bought nothing the own-stack exclusion did not already cover, and left `compose down` unprotected against a name-coincident foreign stack), `_stack_is_ac` is anchored on a real `container_name:` key (a bare grep re-fired the false refusal on any compose that merely MENTIONS an AC image), and the bats docker stub now exits 64 on argv drift instead of answering any `docker ps` — it was validating the parser against the test's own idea of the command.
- **A PORT BIND PROBE ANSWERS A DIFFERENT QUESTION THAN THE ONE THAT MATTERS (2026-08-01/08-02, measured both directions).** The first cold-`start` guard asked "can I bind 3724/8085/7878?" and refused if not. On Windows with Docker Desktop — the only platform the beta ships on — that has NO bearing on whether `docker compose up` will work: a port Docker was already publishing (`netstat` LISTENING, serving HTTP 200) probed **FREE**, and a port a plain `TcpListener` held probed **TAKEN** while `docker run -p …:80` came up on it anyway. So it was inert for the one cause its own message named ("another DML server is already running") and fired for cases where that message was wrong, with no override — a guard that is wrong in both directions is worse than none, because people trust it. It is now `lifecycle::stack_conflict_refusal`, which asks the install guard's question (the engine-global `ac-*` container names) through the same pure helpers (`install_native::parse_stack_owners` / `conflicting_owner`), so the install-time and start-time answers cannot disagree; `ps_output: None` means docker could not answer, which is evidence of NOTHING and never refuses. The 17-entry `CONFLICT_PORTS` sweep survives as an advisory warn, with a floor: **ports at or above `EPHEMERAL_FLOOR` (49152) never warn** (found live 2026-08-02 — a start reported "Port 54230 is already in use -- Final Fantasy XI auth server (Darkstar)" on a box running no such thing; Windows' dynamic range is 49152–65535, so those two Darkstar entries can only ever fire on a transient client socket). That matters more than the noise: the three ports that DO mean something all sit far below the floor, and a user taught to scroll past port warnings is a user who will scroll past those too. **3306 keeps its own branch** — it is the one collision with a real automatic remedy (the `.env` `DOCKER_DB_EXTERNAL_PORT` remap). `dml_core::compose` exposes both `port_listening -> bool` and `port_probe -> Tri`; use the tri-state anywhere a failure to answer must not read as "in use", since `bool` turns a `PermissionDenied` or a Hyper-V-reserved range into a refusal to start a server that works.
- **The `pct` event is live (2026-08-01), and it is the ONE number in this repo that is not a guess.** `{"event":"pct","value":62}`, advisory, no stage name (the consumer reads the stage from the enclosing `section_start`). Emitted by exactly one place: `install_native.rs`'s `build` stage, parsed from **ninja**'s `[1803/1808]` counter in the streamed docker output (AzerothCore's Dockerfile installs `ninja-build`, so the denominator is real and known). Three rules, each from a real build log, and all three are load-bearing: the bracket must be **digits-only** (BuildKit's vertex header carries a Dockerfile-stage `2/4` that would slam the bar to 50% during a 0.1s `mkdir`), the **largest-total vertex wins** (four images build in parallel; a 3-step sidecar must not outbid the 1808-step compile), and the number **never goes down**. Emitted only on change, so a 1808-step build produces ≤101 events. **Four stages report (2026-08-01):** the two clones from git's own counter (`Receiving objects` weighted 0–90, `Resolving deltas` 90–100 — reporting git's four phases raw gives four sawtooths that read as a bug; the server-side three are excluded because their `remote: ` prefix defeats the anchored match), `build` from ninja, and `up` from containers-finished / containers-declared (denominator derived by `composegen::base_container_names()` scanning the template's `container_name:` lines, so a new service counts itself instead of stalling the bar at 80%). `ready` deliberately reports NOTHING: it is a bounded WAIT, so `section_start` carries **`limit_secs`** instead and the frontend renders elapsed ("Waiting for the world… 4:31", Home adds "of up to 30:00") — elapsed-over-timeout measures the clock, not the work, and 97% on a wait about to fail is the worst reading available. **The clone progress needed a dml-core change:** git writes redraws with `\r` and emits `\n` only at PHASE END, so `drain_lines` (which split on `\n` only) delivered a whole download as one line after it finished — hence `LineSplit::NewlineOrReturn`, chosen per call by TOOL (`Program::Git`, never docker, whose build wall uses blank lines that the `\r` mode drops). `run_echo_with`'s hook now also RETURNS whether to echo: the tee always gets every line (a stalled download's evidence), the terminal only gets redraws that moved the number. Frontend: `launcher/src/lib/install-progress.svelte.ts` (module-level runes store + pure reducer, mirrors `restart-state.svelte.ts` so it survives navigation) feeding `statusLabel`, whose precedence is now **installing > restarting > polled verdict**. `install` is a REQUIRED third parameter there on purpose — an optional one lets a call site quietly go back to reporting a compiling machine as an idle server. - **Test-portability rules, learned the hard way:** never hardcode `cmd.exe` or a drive-letter `Path` literal in a test — use a per-platform `#[cfg]` helper (the convention lives in `dml-core`'s `runner.rs`/`proc.rs` and `dml-wow`'s `backup.rs`/`restore.rs`). `std::env::join_paths` rejects a component containing the platform's PATH separator, so `C:\...` entries fail on Unix. Forward-slash path literals work on BOTH flavours; backslash ones are Windows-only.
- **The vacuous-pass trap:** `cargo test` captures `eprintln!` from PASSING tests, so a suite that skips for a BROKEN reason looks identical to one that ran. That is why the Linux CI job runs with `-- --nocapture`, and why every parity suite's `find_bash`/`yq_path` gate is per-platform. When a test's assertion could be satisfied by an early error return, assert something a failed spawn cannot satisfy (e.g. elapsed >= the deadline). **Its sibling: never pin an ordering invariant on a pure list that production never reads** — `lifecycle_steps_for_mode` restated the pre-stop order (`logsnap` → `backup` → `down`) and its 4 tests stayed green when the real snapshot call was moved or deleted. Deleted; the order is now asserted against the real call site (`games_lifecycle_stream_with`, driven via `LifecycleEnv` + a fake `docker` whose calls are read back in order — the same oracle `cli/tests/games-log-snapshot.bats` uses).
- **`cargo test --workspace` STOPS AT THE FIRST FAILING TARGET, so a failure count is a lower bound, not a count (2026-08-06).** A review measured "2 clean-env failures" from a plain `cargo test --workspace`; the same tree under `--no-fail-fast` had **13**, from one root cause, across targets cargo never reached. The 11 invisible ones were not smaller versions of the two — they were different call sites of the same defect, and fixing only what the first run showed would have left the branch red. Always pass `--no-fail-fast` when the question is "how much is broken", and read the totals by summing `test result:` lines rather than trusting the last block printed. Sibling of the piped-tail trap in the root `CLAUDE.md`: both report a healthy-looking number computed from a partial run.
- **An ambient env var makes every local run measure a different thing than CI does (2026-08-06).** This machine exports `DML_GAMES_DIR`, `DML_BACKEND`, `DML_SCRIPT` and `DML_YQ_BIN` as USER env vars, and `.github/workflows/rust.yml` sets none of them. A change that made the DB surface depend on a resolvable games dir passed `cargo test --workspace` for the implementer AND for the reviewer, and would have failed both CI jobs on push. Before believing a workspace-green claim, re-run under `env -u DML_GAMES_DIR -u DML_BACKEND -u DML_SCRIPT -u DML_YQ_BIN` and check the totals are IDENTICAL — a clean run with FEWER tests is a run that skipped, not a run that passed.
- **List order is NOT contractual:** bash `sort(1)` collates per locale (en_US = case-insensitive), Rust `Vec::sort` is byte order. Compare file sets, not positions.
