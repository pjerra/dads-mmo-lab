  - **The two first-boot bugs the LIVE GATE found, both on a genuinely fresh image.** (1) `/etc/sudoers.d` does not exist until the `sudo` PACKAGE is installed — `sudo` is `Required By: base-devel`, not `base` — so the original sudoers-before-pacman order died with `No such file or directory`. (2) A fresh Arch WSL rootfs has **no initialized pacman keyring**, so the very first `pacman -Syu` of any kind fails with `required key missing from keyring` until `pacman-key --init` AND `--populate archlinux` have run. Order is now `wsl-conf → restart → useradd → pacman-key → pacman-sync → sudoers → docker-group → docker-enable`, each edge pinned as a RELATION rather than a copy of the list.
  - **The restart is a STEP, because systemd only becomes PID 1 on the next boot.** `first_boot_steps` returns `FirstBootAction::{InDistro, RestartDistro}` — an enum, not a `restart_after: bool`, so a consumer that iterates the Vec cannot silently skip it (a match missing the arm does not compile), and `RestartDistro` carries the real `terminate_argv` so the Vec is executable as written.

Hence `SetupState::DistroUnprepared` + `SetupStep::Prepared` between Distro and Engine, decided by `command -v docker`, and `classify_arch_dockerd` now treats only exit **3** (systemd's documented "not running") as a stopped engine. - **A BOUNDED CALL WAS NOT BOUNDED, and every docker probe inherited it (2026-08-03).** `dml_core::proc::run_bounded_outcome` killed its child at the deadline and then JOINED the two reader threads before returning — on the stated grounds that killing the child closes its pipes. It does not when the child spawned a GRANDCHILD that inherited the handles: measured, a 600ms-bounded call against `cmd /C ping -n 600` returned after **605 seconds**, while the same child spawned without the shell returned in 0.61s. `docker`, `wsl.exe` and `git` all spawn helpers, so this was every bounded probe in the project quietly losing its bound. The join was A cause and the early return is in (the timeout path **already discarded those buffers**, so the joins bought nothing and cost everything) — but it is **NOT fully fixed**: the pinning test is `#[ignore]`d because it passed twice standalone at 0.63s and then took 605s under a parallel `--workspace` run. `out.is_none()` passed in the slow run, so the deadline DID fire and the time was spent before the early return — which points at the `child.kill()` / `child.wait()` pair inside the poll loop (kill's result is discarded, and the wait then blocks until `cmd.exe` ends by itself). **Pick this up with `cargo test -p dml-core --lib -- --ignored`.** Same round: `engine::start_engine` (`docker desktop start -d`) had **no** wall-clock bound at all — the one command reached specifically because the engine is not answering — now `ENGINE_START_ASK_TIMEOUT` (60s), with a timeout reading as the existing "fall back to the exe".

- **A MOVING IMAGE TAG SILENTLY REPLACED THE USER'S SERVER (live incident, 2026-08-02).** The migration saves the user's OWN built images (`docker save`) and they carry upstream's own tag, `acore/ac-wotlk-<svc>:master`, because that is what the WSL server ran under. Three symptoms, one cause, and nothing in the output named it: **bots did not load** (playerbots was no longer IN the binary — not a config problem), the worldserver logged `mmtile was built with generator v19, expected v20` (upstream's newer build wants newer client data), and `ac-client-data-init` exited 1 trying to fetch v20 — which it could never do, because the volume is root-owned while the container runs as uid 1000, a latent flaw the version bump exposed. Recovery was the user's own `img-*.tar.gz` in the server dir. **The fix, both for that server and in `poc/native-docker/migrate/`: run migrated stacks from `dml.local/ac-wotlk-<svc>:${DML_LOCAL_TAG:-migrated}`**, a namespace no registry serves — a missing image is then a loud `pull access denied` instead of a silent substitution. `check-migrate-scripts.sh` asserts both directions (mutation-proven). **Diagnostic lesson worth as much as the fix:** the first check ran `strings worldserver | grep -c playerbot` and reported 0 — but `strings` is ABSENT from the image, so the `|| echo 0` fallback made "no playerbots" and "no strings binary" indistinguishable. Grepping the binary directly gave 3388, and `worldserver --version` said `(Playerbot branch)` outright. A probe whose failure mode looks exactly like its negative answer is not a probe.
- **THE STACK-CONFLICT GUARD, and the two live bugs it caused (2026-08-02, mirrored bash↔Rust).** The refusal asks the only honest question — do the engine-global `ac-*` container names belong to someone else — but "someone else" was decided by the DERIVED compose project name, and that was wrong twice on real machines. (1) The user's migrated server runs under the project `dml-wow-native`, a migration-era name `composegen::project_name_for` can never produce, so the launcher refused to start **their own server** and told them to go stop it. (2) The bash side compared paths BYTE-wise while Git Bash spells `$PWD` as `/c/Users/...` and the compose label spells it `C:\Users\...`. "Ours" now holds on EITHER signal: the derived name matches, OR `com.docker.compose.project.working_dir` names the directory we are about to compose from — ground truth that survives `COMPOSE_PROJECT_NAME` and top-level `name:`. The ps format is TAB-separated (working dirs hold spaces) and `canon_path`/`_canon_path` fold the four spellings of one directory (`C:\x`, `C:/x`, `/c/x`, `/mnt/c/x`), lowercasing only drive-rooted paths — on Linux `/srv/A` and `/srv/a` really differ. Bash deliberately does NOT use `realpath`: Git Bash's mangles `C:\` into cwd-relative nonsense. Three more rules from the same round: the guard runs on **restart too** (the start-only gate bought nothing the own-stack exclusion did not already cover, and left `compose down` unprotected against a name-coincident foreign stack), `_stack_is_ac` is anchored on a real `container_name:` key (a bare grep re-fired the false refusal on any compose that merely MENTIONS an AC image), and the bats docker stub now exits 64 on argv drift instead of answering any `docker ps` — it was validating the parser against the test's own idea of the command.
- **The port-conflict REFUSAL (2026-08-01, mirrored bash-Rust).** `lifecycle::stack_port_refusal` + `STACK_PORTS` (3724/8085/7878 only - the ports this stack publishes) refuses a cold `start`; the 17-port `CONFLICT_PORTS` sweep stays advisory. **3306 is deliberately excluded**: it is the one collision with a real automatic remedy (the `.env` `DOCKER_DB_EXTERNAL_PORT` remap). Uses the NEW `dml_core::compose::port_probe -> Tri`, not `port_listening -> bool`: the latter reads ANY bind failure as "in use", which is right for a warning and would turn a `PermissionDenied` or a Hyper-V-reserved port range into a refusal to start a server that works.
- **The `pct` event is live (2026-08-01), and it is the ONE number in this repo that is not a guess.** `{"event":"pct","value":62}`, advisory, no stage name (the consumer reads the stage from the enclosing `section_start`). Emitted by exactly one place: `install_native.rs`'s `build` stage, parsed from **ninja**'s `[1803/1808]` counter in the streamed docker output (AzerothCore's Dockerfile installs `ninja-build`, so the denominator is real and known). Three rules, each from a real build log, and all three are load-bearing: the bracket must be **digits-only** (BuildKit's vertex header carries a Dockerfile-stage `2/4` that would slam the bar to 50% during a 0.1s `mkdir`), the **largest-total vertex wins** (four images build in parallel; a 3-step sidecar must not outbid the 1808-step compile), and the number **never goes down**. Emitted only on change, so a 1808-step build produces ≤101 events. **Four stages report (2026-08-01):** the two clones from git's own counter (`Receiving objects` weighted 0–90, `Resolving deltas` 90–100 — reporting git's four phases raw gives four sawtooths that read as a bug; the server-side three are excluded because their `remote: ` prefix defeats the anchored match), `build` from ninja, and `up` from containers-finished / containers-declared (denominator derived by `composegen::base_container_names()` scanning the template's `container_name:` lines, so a new service counts itself instead of stalling the bar at 80%). `ready` deliberately reports NOTHING: it is a bounded WAIT, so `section_start` carries **`limit_secs`** instead and the frontend renders elapsed ("Waiting for the world… 4:31", Home adds "of up to 30:00") — elapsed-over-timeout measures the clock, not the work, and 97% on a wait about to fail is the worst reading available. **The clone progress needed a dml-core change:** git writes redraws with `\r` and emits `\n` only at PHASE END, so `drain_lines` (which split on `\n` only) delivered a whole download as one line after it finished — hence `LineSplit::NewlineOrReturn`, chosen per call by TOOL (`Program::Git`, never docker, whose build wall uses blank lines that the `\r` mode drops). `run_echo_with`'s hook now also RETURNS whether to echo: the tee always gets every line (a stalled download's evidence), the terminal only gets redraws that moved the number. Frontend: `launcher/src/lib/install-progress.svelte.ts` (module-level runes store + pure reducer, mirrors `restart-state.svelte.ts` so it survives navigation) feeding `statusLabel`, whose precedence is now **installing > restarting > polled verdict**. `install` is a REQUIRED third parameter there on purpose — an optional one lets a call site quietly go back to reporting a compiling machine as an idle server. - **Test-portability rules, learned the hard way:** never hardcode `cmd.exe` or a drive-letter `Path` literal in a test — use a per-platform `#[cfg]` helper (the convention lives in `dml-core`'s `runner.rs`/`proc.rs` and `dml-wow`'s `backup.rs`/`restore.rs`). `std::env::join_paths` rejects a component containing the platform's PATH separator, so `C:\...` entries fail on Unix. Forward-slash path literals work on BOTH flavours; backslash ones are Windows-only.
- **The vacuous-pass trap:** `cargo test` captures `eprintln!` from PASSING tests, so a suite that skips for a BROKEN reason looks identical to one that ran. That is why the Linux CI job runs with `-- --nocapture`, and why every parity suite's `find_bash`/`yq_path` gate is per-platform. When a test's assertion could be satisfied by an early error return, assert something a failed spawn cannot satisfy (e.g. elapsed >= the deadline). **Its sibling: never pin an ordering invariant on a pure list that production never reads** — `lifecycle_steps_for_mode` restated the pre-stop order (`logsnap` → `backup` → `down`) and its 4 tests stayed green when the real snapshot call was moved or deleted. Deleted; the order is now asserted against the real call site (`games_lifecycle_stream_with`, driven via `LifecycleEnv` + a fake `docker` whose calls are read back in order — the same oracle `cli/tests/games-log-snapshot.bats` uses).
- **List order is NOT contractual:** bash `sort(1)` collates per locale (en_US = case-insensitive), Rust `Vec::sort` is byte order. Compare file sets, not positions.
