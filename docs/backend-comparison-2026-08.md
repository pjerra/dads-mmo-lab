# Docker Desktop vs Arch WSL — the measurements

**Run:** 2026-08-05, 09:16–10:11 UTC, one continuous sitting, label `run1`.
Boot timing re-measured 12:32–12:38 UTC the same day, label `run2` (see below).
**Method:** [`docs/backend-comparison-method.md`](backend-comparison-method.md).
**Harness:** `scripts/Measure-BackendFootprint.ps1` (20 samples, all clean, none
forced) and `scripts/Compare-BackendFootprint.ps1`.
**Raw output:** `results/backend-comparison/` — 10 JSON records plus
`samples.csv` and `run2-ready-timing.json`. That directory carries its own
`.gitignore` containing `*`, so it is deliberately **not committed**; every
number below is therefore reproduced in the tables here, which are the durable
copy, and the directory is regenerated by re-running the procedure.

**What "20 samples" means, because it is easy to misread as n=20.** Twenty
sample *records*: ten per backend, spread across five phases. Four of those
phases were sampled **once** per backend (`off`, `engine`, `server`, `disk`);
only `stopped` was repeated, six times at 30 s intervals. **So every row that
carries the verdict is n=1 per backend** — including the headline idle saving.
The one finding in this document with a real distribution behind it is the 15 s
distro termination (n=8, spread 0.2 s), and that contrast is deliberate: it is
the difference between a number you can plan on and a number you should
re-measure before betting on it. Each claim below states its own n.

## Read this before any number below

Five things limit what this run can honestly claim. None of them is buried
later in the document; they are here because they change how every table reads.

### 1. The two servers are not configured alike, so the "server" phase is NOT a backend comparison

This is the single most important finding of the sitting, and it was found by
reading the config rather than by trusting the labels:

| | Docker Desktop (`C:\Users\perzi\dml-native`) | Arch WSL (`~/games/wow-server-playerbots`) |
|---|---|---|
| `playerbots.conf` Min/MaxRandomBots | 100 / 100 | 500 / 500 |
| compose override env | *(no bot keys)* | `AC_AI_PLAYERBOT_MIN_RANDOM_BOTS=1600`, `..._MAX_...=2000` |
| **effective, online (operator-reported)** | **100** | **1,948** |

The env override wins over the conf file, so the Arch server ran **19.5× the
workload**. Changing either config was forbidden for this run, so the servers
were measured as they actually are. **The `server` and `stopped` rows therefore
compare two different workloads, not two backends.** They are reported because
they are real, not because they answer the question.

The phase that *is* a controlled comparison is **`engine`** — engine up, zero
containers, identical state on both sides. That row carries the verdict.

### 2. On a full box, "RAM in use" drifts more than the effect being measured

The harness's headline metric is machine-level `Total − Available`, corrected
against an `off` baseline. Two readings of the *same* idle state were recorded
across this sitting — the two `off` baselines, one per backend:

| Idle reading (n=1 each) | In use | Committed | Source row |
|---|---|---|---|
| Desktop `off` baseline, 09:18:01Z | 24,815.5 MB | 39,561.8 MB | `samples.csv` line 2 |
| Arch `off` baseline, 09:40:40Z | 22,210.5 MB | 39,418.8 MB | `samples.csv` line 12 |
| **spread over 22 minutes** | **2,605.0 MB** | **143.0 MB** |  |

The machine's own idle "in use" moved by **2.6 GB** between the two baselines
while *committed bytes* moved by **143 MB**. The cause is working-set trimming:
the server phases drove the box to ~250 MB available, and Windows evicted the
pages of every unrelated process, so the same idle state reads progressively
lower. The drift (2.6 GB) is **larger than the idle difference being measured**
(≈1.0–1.6 GB).

> **Correction, 2026-08-05.** An earlier version of this section showed a third
> idle reading ("end of sitting, 10:11 — 21,393.5 MB / 39,361.5 MB") and a
> spread of 3,422.0 / 200.3 MB. **No such sample exists.** The sitting's last
> record is the `stopped` series at 10:10:49Z, which is not an idle state — the
> distro and `dockerd` were still up. Those figures were never written to
> `samples.csv` or to any JSON and are withdrawn. The two baselines above are
> the whole of the recorded evidence for drift, and the argument survives on
> them: 2.6 GB of drift against a 1.0–1.6 GB effect. Note the *contrast* the
> section exists to draw is sharper on the real numbers, not weaker — 2,605
> against 143 is an 18× ratio where the withdrawn figures gave 17×.

**Consequence: committed bytes is the trustworthy metric on this box, and every
table below reports both.** Where they disagree, believe committed.

### 3. Both `server` samples hit the machine's physical ceiling

At the moment of sampling, physical memory available was **249 MB** (Desktop)
and **268 MB** (Arch) of 31,936.5 MB. The box was out of RAM in both cases.
Working-set figures taken there are suppressed by paging pressure, not by
demand. The 16 GB `.wslconfig` cap was *not* reached (VM private peaked at
**10,191.3 MB**, the Arch `disk` sample, `samples.csv` line 15), so the ceiling
that bit was the host's, not WSL's.

### 4. The box was not idle, and I could not make it so

The user was asleep and their session was live. Throughout the sitting: 289
processes, ~12.6 GB of working sets, 22 VS Code processes (2.69 GB),
rust-analyzer (1.70 GB), TeamViewer (583 MB), two `claude` processes (548 MB),
Edge WebView2 (419 MB), Defender (398 MB), tailscaled (185 MB), Task Manager
open. **No compile or build ran at any point**, and nothing was started or
stopped between the two halves except the backends themselves. Closing the
user's editor was not authorised, so this noise is present in both columns and
is the main reason the drift in §2 exists.

`vmmemCmZygote` (806 MB private) ran throughout. It is a Windows
container-manager VM, nothing to do with WSL; the harness matches VM processes
by exact name so it is excluded from every figure here. That one is checkable:
the figure and the reason are recorded at
`scripts/Measure-BackendFootprint.ps1:180-185`, and a self-test case fails the
run if `vmmemCmZygote` ever enters the VM name list.

**Provenance note (added 2026-08-05).** The per-application figures in this
paragraph — process count, total working sets, and the individual apps — were
observed live during the sitting and are **not in the sample records**. The
harness stores per-process detail for only two families, Docker Desktop's
processes and the WSL plumbing; it does not enumerate the rest of the machine.
They are kept because they were contemporaneously noted and they describe
conditions rather than results, but they cannot be re-checked against
`samples.csv`, and no conclusion in this document rests on them. What *is*
recorded, and what actually carries §4's point, is the machine level: an `off`
baseline of **24,815.5 MB in use of 31,936.5 MB** is by itself proof that the
box was nowhere near idle.

### 5. The Arch column's `0 MB / 0 procs` is a precondition, not a property — and it decides the answer for anyone who keeps Docker Desktop

Every sample record in this run carries this sentence, written by the harness
itself (`Get-NotMeasured`, one of five `notMeasured` entries in all 10 JSONs):

> *Docker Desktop's Windows-side memory in the Arch column: it is zero only
> because Desktop is required to be exited. Any user who keeps Desktop installed
> and running for other work pays it on both backends.*

This matters more than any other caveat here, because **≈590 MB of the claimed
1.0–1.6 GB saving is exactly that cell**. The comparison below measures Arch
against Desktop *with Desktop shut down*. That is the right control for "which
backend is cheaper", and it is the wrong model of a user who runs Docker Desktop
for other work and would keep it running regardless.

For that user the 586.5 MB appears in **both** columns and cancels out of the
difference. Subtracting it from the measured deltas:

| Idle saving, engine phase (n=1 per backend) | In use | Committed |
|---|---|---|
| As measured, Desktop exited | 1,016.0 MB | 1,607.1 MB |
| less Desktop's Windows processes, paid on both sides | −586.5 MB | −586.5 MB |
| **for a user who keeps Desktop running** | **429.5 MB** | **1,020.6 MB** |

**So the honest range for that user is ≈0.4–1.0 GB, not 1.0–1.6 GB — and that
is an upper bound.** The other ~840 MB of the saving is extra WSL *utility VM*,
and it is extra only because Desktop's `docker-desktop` distro is a second Linux
system inside it. A user with Docker Desktop running has that distro up too, so
that component would erode as well, and it could erode most of what is left.
**How much cannot be stated**: the harness *refuses to sample when more than one
distro is running* (that refusal is what makes the single VM figure attributable
at all), so the both-distros-up state was never measured and no number for it
exists. The direction is not in doubt; the magnitude is unmeasured, and inventing
it here would be the same error this section is correcting.

## The controlled comparison: engine idle

Engine up, **zero containers**, no server, nothing else running. Same state
both sides. This is the row that answers the question.

**n=1 per backend.** One `engine` sample was taken on each side (`samples.csv`
lines 3 and 13), each differenced against that backend's single `off` baseline
(lines 2 and 12). Every figure in this table is therefore a difference of two
single readings, with no repeat and no spread — on a box whose idle drift over
22 minutes was 2.6 GB (§2). The three-way agreement noted below is the reason to
trust it anyway, and it is not a substitute for repetition.

| | Docker Desktop | Arch WSL | Arch saves |
|---|---|---|---|
| Machine in use, over `off` baseline | +2,798.0 MB | +1,782.0 MB | **1,016.0 MB** |
| Machine committed, over `off` baseline | +3,806.4 MB | +2,199.3 MB | **1,607.1 MB** |
| WSL utility VM, working set | 2,233.0 MB | 1,393.1 MB | 839.9 MB |
| WSL utility VM, private | 2,302.3 MB | 1,460.7 MB | 841.6 MB |
| Docker Desktop Windows processes | 586.5 MB / 8 procs | 0 MB / 0 procs | 586.5 MB |
| WSL Windows-side plumbing | 121.9 MB / 10 procs | 91.5 MB / 7 procs | 30.4 MB |

**Where the difference comes from.** Summing the three attributable components
— VM 839.9 + Desktop processes 586.5 + plumbing 30.4 = **1,456.8 MB** — lands
between the two machine-level deltas (1,016 and 1,607 MB). The three
independent measurements agree, which is the main reason to trust this row.

So the saving is roughly **1.0–1.6 GB at idle**, and it is **two effects of
similar size**, not one:

* **~590 MB** of Docker Desktop's Windows-side processes, which Arch simply
  does not have; and
* **~840 MB** of extra WSL utility VM, because Desktop's `docker-desktop`
  distro is a second Linux system running inside the same VM.

Neither alone would be the story. Attributing the whole saving to "no Docker
Desktop app" would be wrong by about half.

**Both components assume Docker Desktop is shut down**, which is a precondition
of the measurement rather than a fact about the user. If you keep Desktop running
for other work, read §5 before using the 1.0–1.6 GB figure: the first component
cancels outright, taking the saving to **≈0.4–1.0 GB**, and the second erodes by
an amount this run cannot quantify.

## The uncontrolled rows: server up, and after stop

Reported for completeness. **These compare 100 bots against 1,948 bots.**
**n=1 per backend** (`samples.csv` lines 4 and 14).

| | Docker Desktop (100 bots) | Arch WSL (1,948 bots) |
|---|---|---|
| Machine in use, over baseline | +6,872.0 MB | +9,458.0 MB |
| Machine committed, over baseline | +10,881.0 MB | +10,813.6 MB |
| WSL VM working set | 8,199.4 MB | 9,933.1 MB |
| WSL VM private | 9,494.7 MB | 10,140.6 MB |
| Physical RAM available at sample | 249 MB | 268 MB |
| Bots online (**operator-reported**, not measured) | 100 | 1,948 |

The bot counts are the **operator's claim**, recorded by the harness as
`botsOnlineOperatorReported` and listed in every record's own `notMeasured`
array: *"Bots actually online. That needs SOAP or MySQL; `-BotsOnline` records
the OPERATOR's claim and is not a measurement."* The controller's report for the
sitting states that a `SELECT COUNT(*)` against `characters.online=1` was run to
obtain them, so the figures are very probably right — but that query's result was
never captured into any record, so what survives in the data is an
operator-entered integer. Treat them as the workload the servers were
*configured* for and confirmed by eye, not as a measured population.

Both samples were taken at **T0 + 575 s** from the worldserver container start,
with the bot population plateaued in both cases (Desktop from T0+122 s, Arch
from T0+177 s), so the *protocol* was identical even though the workload was
not.

One observation worth recording, and worth its own controlled test before
anyone relies on it: **19.5× the bots cost only ~646 MB more VM private memory**
(9,494.7 → 10,140.6 MB). That is consistent with AzerothCore's fixed cost — map
data, DBC, the world database, the MySQL buffer pool — dominating, with each
additional bot session comparatively cheap. But the two stacks differ in build,
in database contents and in image lineage, so this is a *suggestion from two
uncontrolled points*, not a measurement of the marginal cost of a bot.

### After stop (engine still up), 6 samples 30 s apart

**n=6 per backend** (`samples.csv` lines 6–11 and 16–21) — the only phase in the
sitting that was repeated at all.

| Sample (t after settle) | Desktop in use | Desktop VM WS | Arch in use | Arch VM WS |
|---|---|---|---|---|
| 1 (t+0 s) | 27,352.5 MB | 4,426.5 MB | 25,696.5 MB | 4,018.6 MB |
| 2 (t+30 s) | 27,367.5 MB | 4,419.8 MB | 25,699.5 MB | 4,018.6 MB |
| 3 (t+60 s) | 27,381.5 MB | 4,394.5 MB | 25,685.5 MB | 4,008.1 MB |
| 4 (t+90 s) | 27,332.5 MB | 4,387.6 MB | 25,655.5 MB | 3,993.0 MB |
| 5 (t+120 s) | 27,343.5 MB | 4,375.8 MB | 25,665.5 MB | 3,898.2 MB |
| 6 (t+150 s) | 27,306.5 MB | 4,292.4 MB | 25,481.5 MB | 3,807.4 MB |
| **VM drop over the series** | **−134.1 MB** | | **−211.2 MB** | |

**This is not a differentiator, exactly as the method predicted.** Both curves
are nearly flat: with `autoMemoryReclaim=gradual`, WSL returns freed guest
memory to Windows on an undocumented schedule, and 150 s of it returns 3–5% of
the VM. Both backends leave the VM sitting far above where it started
(Desktop 4.29 GB and Arch 3.81 GB against engine-idle figures of 2.23 GB and
1.39 GB). That is a property of the WSL2 utility VM, shared by both, and the
number you get depends mostly on how long you waited.

The only state in which all memory is provably returned is the one where the VM
process is **gone**, and that was reached identically on both sides: at both
`off` baselines and at the end of the sitting, `vmmemWSL` was absent entirely.

## Time from start to world-ready

> **This section was re-measured on 2026-08-05 and its earlier numbers are
> withdrawn.** The `run1` sitting reported 28.6 s vs 24.6 s with eight
> supporting timestamps. **None of it was recorded.** All 20 `run1` records
> carry `"ready": null`, and every `readyMarkerSec` / `readyTcpSec` cell in
> `samples.csv` is empty — the harness's `-TimeReady` phase was never run. The
> figures below are a fresh measurement, label `run2`, raw record
> `results/backend-comparison/run2-ready-timing.json`, with the full timestamps
> reproduced here because that directory is not committed.

Measured by the product's own definition — `docker inspect .State.StartedAt`,
then `docker logs -t --since <started>` scanning for `world initialized in`,
mirroring `crates/dml-wow/src/status.rs::world_ready`. **T0 → world-ready is
derived from the marker line's own log timestamp**, not from when a poll loop
noticed it, so poll granularity does not inflate it. The TCP row is the
exception and is poll-derived, marked as such.

| | Docker Desktop | Arch WSL |
|---|---|---|
| T0 — `docker compose up -d` issued | 12:32:58.288Z | 12:37:29.683Z |
| worldserver container `StartedAt` | 12:33:06.374Z (T0+8.1 s) | 12:37:36.906Z (T0+7.2 s) |
| `World Initialized` logged | 12:33:31.353Z | 12:37:53.155Z |
| **T0 → world-ready** | **33.1 s** | **23.5 s** |
| `StartedAt` → world-ready | 25.0 s | 16.2 s |
| worldserver's own self-report | "0 Minutes 23 Seconds" | "0 Minutes 15 Seconds" |
| TCP 8085 first accepted *(poll-derived)* | T0+8.2 s | *(not captured — see below)* |
| `docker compose down` wall clock | 10.1 s (cold, no bots yet) | *(not captured)* |

The `run1` shutdown figures **were** recorded and are kept: **6.5 s** to tear
down the 100-bot Desktop stack and **12.6 s** for the 1,948-bot Arch stack,
both in the `note` field of the `stopped` rows of `samples.csv` (lines 6–11 and
16–21). Those two are a workload comparison, not a backend one. The 10.1 s above
is a different thing again — a stack taken down seconds after world-ready, before
any bot logged in.

**The arithmetic checks against a witness.** The worldserver reports its own
world-load time independently of anything measured from outside, and on both
sides it agrees with the log-derived figure: Desktop 23 s against a measured
25.0 s from `StartedAt`, Arch 15 s against 16.2 s. The ~1–2 s residual is
container start before world load begins. That is a check on the arithmetic,
not on the comparison.

Both stacks started from **containers removed but images and volumes present**,
verified by `docker ps -a` returning empty on each side before T0 — the script
refuses to start otherwise, so a warm start cannot be misreported as a cold one.
Neither run rebuilt or pulled: `--no-build --pull never` on **both** sides, which
on the Arch stack is mandatory (it carries `build:` sections and moving
`acore/ac-wotlk-*:master` tags — the exact shape that silently replaced this
user's images once before) and on the Desktop stack is belt-and-braces (pinned
`dml.local/ac-wotlk-*:migrated-20260720`, no `build:` sections).

**A 9.6-second difference is still not a meaningful backend advantage, and this
measurement is weaker than the RAM rows, not stronger.** n=1 per backend, one
boot each. Three things confound it, and they all push the same way:

* **The servers are not configured alike** — the same 100-vs-1,948-bot defect
  that voids the `server` phase (§1). Bots log in *after* world-ready, so the
  effect is smaller here than on the RAM rows, but it is not zero.
* **The two halves did not run under equal load.** During the Desktop boot the
  host fell to **926 MB available** with two compiler processes running (a
  concurrent Rust build in a separate worktree). Host memory was *not* sampled
  during the Arch boot, so the halves cannot be claimed to have run under equal
  pressure. The Desktop figure is the one more likely inflated.
* **Page-cache warmth differed**: the Arch distro had been touched by two brief
  `wslpath` probe sessions shortly before its measurement.

The honest reading is unchanged from the earlier draft even though the numbers
moved: **both backends reach world-ready in well under a minute**, and nothing
here should decide a backend choice.

**The method's warning about the cheap probe is confirmed, on the Desktop run
this time.** TCP 8085 accepted at **8.2 s** against a true world-ready of
**33.1 s** — **24.9 s early**. A readiness check built on the port would have
reported the boot as taking **25% of its real duration, i.e. 75% shorter than it
was**. The Arch TCP figure was lost: `bc(1)` is not installed in `dml-arch`, so
the in-guest script's arithmetic failed. The timestamps survived that failure
because they are strings and were differenced on the Windows side — which is why
the world-ready numbers are unaffected and the TCP one is simply absent.

> A second correction while here: the withdrawn text said the port probe "would
> have reported a boot **47% shorter** than it was", from 11.5 s against 24.6 s.
> Even taking those numbers at face value that is the wrong reading of the
> ratio — 11.5 is 47% **of** 24.6, which is 53% shorter. The re-measured figures
> above state both forms so the mistake cannot recur.

| Local volumes | 16.72 GB (10.03 GB reclaimable; 6 / 2) | 10.53 GB (0 reclaimable; 3 / 2) |

| **Excluding build cache** | **26.62 GB** | **14.03 GB** |

Arch's engine holds three times Desktop's — and **every bit of the difference

on images plus volumes.

68.39 GB of the Arch build cache is reclaimable. Reclaiming it was **not** done
— `docker builder prune` was outside what this run was authorised to do — but
it is the single largest recoverable item on the machine.

## Windows-side processes: the claim, confirmed and corrected

The method predicted ~740 MB of Docker Desktop processes surviving an engine
stop, against ~23 MB for Arch's plumbing. Measured:

| State | Docker Desktop procs | WSL plumbing | Total Windows-side |
|---|---|---|---|
| Desktop, engine + server running | 548.6–586.5 MB / 8 procs | 121.9 MB / 10 procs | ≈708 MB |
| Arch, distro + server running | 0 MB / 0 procs | 91.5 MB / 7 procs | ≈92 MB |
| Everything off (both baselines) | 0 MB | 25.1 / 25.7 MB / 1 proc | ≈25 MB |

**Confirmed:** while running, Docker Desktop costs **≈617 MB more Windows-side
process memory** than Arch (708 vs 92). Arch's Windows-side presence is one
`wslservice` plus a handful of `wslhost`/`wslrelay` helpers. The `0 MB / 0 procs`
cell is a precondition of the measurement, not a property of the Arch backend —
see §5.

**Corrected, two ways:**

1. **The figure is ~590 MB, not ~740 MB.** Across 8 processes, Docker Desktop's
   `desktopWinWsMB` spanned **548.6–586.5 MB** over the nine Desktop samples in
   `samples.csv` (lines 3–11): min 548.6 at the fourth `stopped` sample, max
   586.5 at `engine`. The method's 740 MB was taken on a different day and is
   not reproduced.

   > **Correction, 2026-08-05.** This range was previously printed as
   > "551.8–594.2 MB", which is wrong at **both** ends. 594.2 appears nowhere in
   > the run — no JSON, no CSV cell; and 551.8 is not the minimum, it is merely
   > the `server` sample. The true bounds are 548.6 and 586.5. The claim the
   > sentence exists to make — that the real figure is ~590 MB rather than the
   > method's ~740 MB — is unaffected, and if anything the tighter real range
   > (37.9 MB wide, not 42.4) supports it slightly better.
2. **Nothing survives `docker desktop stop` on this version.** The method's
   three-state table lists "running, engine stopped" as costing ~740 MB. On
   this box (Docker Desktop with engine 29.6.2), `docker desktop stop` **exits
   the application entirely**: 0 processes remained, and `docker desktop status`
   answered *"Could not retrieve status. Is Docker Desktop running?"*. So the
   "740 MB left behind after you stop the engine" cost **does not exist by that
   route**.

   It is still real for the user who leaves the app running, which is the normal
   tray behaviour — but on this machine **`AutoStart = False`**, and Docker
   Desktop is not in `HKCU\...\Run`. This user does not pay it at login.

## The finding that was not on the list: WSL terminates dml-arch under a live server

While measuring, the Arch distro shut itself down **with 1,948 bots online**.
It was not an out-of-memory kill and not a crash. The guest kernel log names it:

```
[Wed Aug  5 11:55:15 2026] WSL (2 - init-systemd(dml-arch)) ERROR:
InitTerminateInstanceInternal:2763: systemctl poweroff did not terminate the
instance in 10000 ms, calling reboot(RB_POWER_OFF)
```

WSL asked the instance to power off ~25 s after the last `wsl.exe` client
exited, and force-cut it when systemd did not finish in 10 s. Corroborating
evidence, all collected: `OOMKilled=false`, `ExitCode=0`, empty `Error`; no
`oom-kill` or `Out of memory` anywhere in `dmesg`; guest and host clocks
identical to the second (09:56:33Z both), so the timeline is not skew.

It reproduces on demand in the idle case. Booting the distro (systemd PID 1,
`dockerd` **active**) and then simply not touching it:

| t after last client exit | `dml-arch` state | `vmmemWSL` |
|---|---|---|
| 0 s | Running | 1,406 MB |
| 20 s | **Stopped** | 944 MB |
| 40 s | Stopped | 879 MB |
| 81 s | Stopped | **absent** |

**Docker Desktop's distro never did this.** It stayed `Running` across every
gap in the Desktop half, including a 180-second window with no client activity
at all, because `com.docker.backend` holds it open from the Windows side.

Two consequences:

* **Every Arch measurement here required an explicit holder.** A `sleep` process
  was run inside the distro to keep the state alive long enough to sample it,
  and that is noted in each affected record. Its cost is one process in the
  guest plus one `wsl.exe` on Windows, and it is inside the Arch column's
  figures.
* **The Arch idle figure of +1,782 MB / +2,199 MB is what it costs while
  *held open*.** Left genuinely alone, an idle Arch backend decays to **zero**
  — distro terminated, VM process gone — which Docker Desktop does not do. That
  is a larger advantage than the table shows, and a liability at the same time,
  because the same mechanism takes a running server with it.

### The cause, established 2026-08-05

The mechanism was chased down the next day and is no longer open. Full workings,
including every mitigation tested and the launcher change it implies:
[`docs/superpowers/plans/2026-08-05-wsl-distro-lifetime.md`](superpowers/plans/2026-08-05-wsl-distro-lifetime.md).
The short version:

**WSL 2.7.10 terminates a distro instance ~15 s after the last `wsl.exe` client
session *into that distro* exits, regardless of what is still running inside it.
The timer is reset only by another session into that distro, and no
configuration key anywhere changes or disables it.**

Measured with an oracle that never calls `wsl.exe` during the observation window
(a heartbeat from a systemd unit inside the guest, watched from Windows by file
length — polling with `wsl --list` would have measured the harness itself).
**Eight unattended runs: 14.7–14.9 s, median 14.8, spread 0.2 s.** This is not a
"sometimes".

* `vmIdleTimeout` is a **second, independent stage** and not the one that
  matters: it governs when the empty *VM* exits, measured at distro death + 61.8 s.
  Setting `vmIdleTimeout=-1` was tested directly — **the distro still died at
  14.8 s** and the VM then never exited. It fixes nothing and makes the idle
  cost permanent, i.e. it destroys the only thing the Arch backend wins.
* The guest journal names the caller: `poweroff requested from client PID 577
  ('systemctl') (unit init.scope)` — WSL's own init. `dockerd` then logs
  `Daemon shutdown complete`. The containers were **stopped gracefully**, which
  is exactly why `OOMKilled=false` / `ExitCode=0` fitted nothing crash-shaped.
* The 25 s in the incident vs 15 s at idle is the same event: 15 s idle timer,
  then WSL's 10 s grace expiring because systemd could not stop 1,948 bots in
  time, hence `reboot(RB_POWER_OFF)`.

The guess above — that launcher polling would mask it — was **half right, and the
half that is wrong is the important half.** A session into the distro every 7 s
does hold it (proven by causation: stop polling, it dies 14.0 s later). But
`wsl --list --verbose` every 7 s does **not** (dead at 14.8 s despite 8 polls),
and a session every 20 s does not either. And the launcher's poll is a
`setInterval` in a WebView2 webview that **hides to tray on close** — the exact
state in which Chromium-family engines throttle timers past the 15 s budget. So
the keep-alive must be an explicit, Rust-owned held session, not a side effect of
the status poll.

`restart: unless-stopped` (set on 3 services) does not prevent any of this. It
makes the outage *self-healing on next touch*: the next `wsl -d dml-arch …` boots
the distro and `dockerd` restores the stack. The user therefore sees a server
that is up every time they look at it and down whenever their friends try to
connect.

## Verdict

**Does running Docker in an Arch WSL distro save meaningful resources versus
Docker Desktop? Yes at idle, by about 1.0–1.6 GB with Docker Desktop shut down,
or ≈0.4–1.0 GB if you keep Desktop running — and that is the whole of it.**
The saving splits roughly evenly between Docker Desktop's ~590 MB of
Windows-side processes and the ~840 MB its `docker-desktop` distro adds to the
shared WSL utility VM, which is exactly why the second figure is so much lower:
a user who keeps Desktop running pays the first component on both backends, so
it cancels (§5). Time to world-ready (33.1 s vs 23.5 s) and engine disk excluding
build cache (26.6 GB vs 14.0 GB) are close enough that neither decides anything.

**Read every number in this verdict with its sample count, because they are not
alike.** The idle saving is **n=1 per backend** — a difference of two deltas,
each from a single sample, on a box whose own idle reading drifted 2.6 GB in
22 minutes. The world-ready figures are **n=1 per backend** too, taken under
unequal host load. The disk figures are single `docker system df` readings.
Against all of that, the 15-second distro termination — the finding above, and
the one the next section says outranks this whole question — is **n=8, spread
0.2 s**. If exactly one thing here has to be true, it is that one.

**The honest qualification is that this is less dramatic than "substantial".**
On a 31.9 GB box a 1–1.6 GB idle saving is 3–5% of RAM — 1.3–3.2% for a user who
keeps Docker Desktop running, and unquantified but smaller again once that
user's `docker-desktop` distro is counted (§5). It vanishes into the
noise the moment a server is running (where the workload dominates by a factor
of ten), and the two most eye-catching numbers available — 87 GB of vhdx and a
9.9 GB image store — turn out on inspection to be a source build cache and a
pile of superseded image tags rather than a difference between the backends.
The one place the Arch backend wins decisively is a case the harness cannot
score: left alone, it stops costing anything at all, because WSL tears it down
— and the same mechanism will take a running server down with it.

### The qualification that outranks the resource question (2026-08-05)

**As it stands, `Backend::Arch` cannot host a server unattended.** 15 s after the
last `wsl.exe` session into `dml-arch` exits, WSL powers the distro off with
whatever is running inside it. Eight measured runs, 0.2 s spread, no
configuration that prevents it. That is not a footnote to a RAM comparison; it
is the difference between a backend that saves a gigabyte and a backend that
cannot do its job.

It is fixable and the fix is measured to work: the launcher must hold one
long-lived `wsl.exe --exec /bin/sleep infinity` session for as long as the
server should run — one Windows process and one guest `sleep`, touching no
user-owned state. That work was specified in
[`docs/superpowers/plans/2026-08-05-wsl-distro-lifetime.md`](superpowers/plans/2026-08-05-wsl-distro-lifetime.md)
and **shipped on 2026-08-05** as `launcher/src-tauri/src/wsl_keepalive.rs`.
Measured against the real distro: held for 62.1 s — 4.1× the deadline — and
died 16.5 s after the holder was released, which is the half that makes the
holder the cause rather than a coincidence. It was **required before the Arch
backend could be offered for running a server**, not an optimisation, so the
paragraphs below now describe a paid bill rather than an outstanding one.

Two consequences for the comparison above:

* **Part of the Arch idle saving was a bill not yet paid.** Docker Desktop spends
  some of its ~590 MB of Windows-side processes doing exactly this babysitting,
  deliberately. The Arch column now carries its equivalent — one `wsl.exe` and
  one guest `sleep`, a few MB, so the 1.0–1.6 GB figure survives essentially
  intact. What changes is the reading, not the arithmetic: the saving is no
  longer partly an unpaid cost.
* **Even fixed — and it is now fixed — the contract is "the server runs while
  the launcher runs."**
  Server-up with no DML process on Windows at all is not achievable on the Arch
  backend by any mechanism found; matching Docker Desktop there would mean
  shipping a Windows service. If unattended hosting matters, that is a point for
  Docker Desktop that launcher work does not erase.

## Provenance

`Compare-BackendFootprint.ps1 -Label run1` reported: **20 samples loaded, 20
clean** — ten per backend over five phases, four of which are n=1 (see the note
under the header) — no forced samples, no shared VM generation between backends,
all backend/phase pairs present. The mandatory `wsl --shutdown` was performed
between the halves and confirmed (VM absent, Docker Desktop absent, both
distros Stopped) before the Arch baseline was taken. Order was all-Desktop,
crossing, all-Arch, never alternating.

**Harness defect found and fixed during the run.**
`Measure-BackendFootprint.ps1` built its docker argv with
`ProcessStartInfo.ArgumentList`, which **does not exist on .NET Framework** —
it was added in .NET Core 2.1, and Windows PowerShell 5.1 runs on .NET
Framework 4 (measured here: PSVersion 5.1.26100.8875, CLR 4.0.30319,
`$psi.ArgumentList -eq $null`). `pwsh` is not installed on this machine. Every
`-QueryDocker` sample therefore died with *"You cannot call a method on a
null-valued expression"* — a **null property**, so the message named the symptom
and not the cause — which would have silently cost the entire disk comparison,
the one number the method identifies as the only like-for-like disk answer. The
file declares itself 5.1-compatible in its own `.NOTES`. Fixed by building the
command line with a `ConvertTo-Win32Arg` helper that follows the
`CommandLineToArgvW` quoting rules; verified by the `-QueryDocker` samples that
produced the disk tables above. The precondition self-test still passes 13/13.

### The boot-timing re-measurement, `run2` (2026-08-05, 12:32–12:38 UTC)

The `run1` boot figures had no sample behind them, so they were taken again. The
procedure followed the method: **all-Desktop, mandatory `wsl --shutdown`
crossing, all-Arch, never alternated**, with the crossing verified (both distros
Stopped, `vmmemWSL` absent, 0 Docker Desktop processes) before the Arch half.
Both halves refused to start unless `docker ps -a` was empty first, so neither
number can be a warm start mislabelled as a cold one, and both used
`--no-build --pull never`.

**`-TimeReady` was not used, and that is why the figures are not in the harness
schema.** Two properties make it the wrong instrument for this: it does not
start the server (it prints *"Trigger the start NOW"* and waits, so T0 and the
start are two different events performed by two different hands), and its
`MarkerSeconds` is **poll-derived on a 5 s sleep loop** — which cannot support
the claim, made in this document's own boot section, that the numbers are
timestamp-derived rather than poll-noticed. A single foreground script was used
instead: it records T0 immediately before issuing `compose up`, then takes the
ready instant from the marker line's **own** `docker logs -t` timestamp. That is
a stricter derivation than the harness offers, at the cost of the record living
in `run2-ready-timing.json` rather than in `samples.csv`.

**The Arch half ran entirely inside one `wsl.exe` session**, so the ~15 s
post-session termination documented above could not fire mid-measurement and no
separate holder process was needed — the session *was* the holder.

One in-guest defect: `bc(1)` is not installed in `dml-arch`, so the script's
arithmetic failed on the Arch side. It cost the Arch TCP-8085 figure and nothing
else — the timestamps are strings, survived unharmed, and were differenced on
the Windows side. The missing figure is reported as missing rather than
back-filled from the Desktop half.

### What could not be measured honestly

* **What either backend costs with Docker Desktop *also* running.** The harness
  requires Desktop to be exited for the Arch samples, which is why its
  Windows-side column reads `0 MB / 0 procs` — a precondition, not a property.
  Every record says so in its own `notMeasured` array. **This is the caveat most
  likely to change a decision**, because ≈590 MB of the 1.0–1.6 GB headline is
  that one cell: for a user who keeps Desktop running it is paid on both
  backends and cancels, taking the saving to **≈0.4–1.0 GB**, and the ~840 MB VM
  component would erode further by an amount that *cannot* be stated — the
  harness refuses to sample with two distros up, so the state was never
  measured. See §5. This limit is listed here because the earlier version of
  this document omitted it entirely while quoting the figures that depend on it.
* **Per-distro RAM.** All distros share one utility VM and one kernel, and
  `/proc/meminfo` is not namespaced, so a distro asked about its own memory
  reports the whole VM's. No split was invented; the harness refuses to sample
  when more than one distro is running, which is what makes the single VM
  figure attributable at all.
* **Any distribution around the RAM figures.** Four of the five phases were
  sampled once per backend, so `off`, `engine`, `server` and `disk` are all
  n=1 — no repeat, no spread, no error bar. Only `stopped` (n=6) and the
  separately-measured distro termination (n=8) have more than a single point.
* **The kernel's share within the VM** — page cache, slab, tmpfs. Real memory
  the backend causes to be used, belonging to a shared kernel, assignable to
  neither.
* **RAM returned after stop, as a difference between backends.** Reported above
  as a curve, per the method. It is a property of WSL, not of either backend.
* **A like-for-like server-load comparison.** Blocked by the 19.5× config
  difference in §1, which could not be corrected without a forbidden config
  change.
* ~~**Whether the server survives unattended.**~~ **Answered 2026-08-05: it does
  not.** WSL powers the distro off ~15 s after the last session into it exits
  (8 runs, 14.7–14.9 s). A distro session every 7 s does prevent it; a
  `wsl --list` poll every 7 s does not, and neither does a session every 20 s.
  See the "cause" subsection above and
  [`docs/superpowers/plans/2026-08-05-wsl-distro-lifetime.md`](superpowers/plans/2026-08-05-wsl-distro-lifetime.md).
* **A quiet machine.** The user's session was live throughout; see §4.
