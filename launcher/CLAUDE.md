- **AUTO-SHUTDOWN KILLED A 90-MINUTE BUILD AND WEDGED THE DOCKER ENGINE (2026-08-15, live on the VM).** `module rebuild` stops ONLY `ac-worldserver` and then compiles for an hour with `ac-database`/`ac-authserver` still up — and `server-detail` reports that partial stack as `soap_unreachable`, which the shared `verdict_needs_stop` counts as "needs stopping". The player closed WoW mid-compile, the watcher fired, ran `games stop`, and because **"Stop Docker Desktop when the server stops" is DEFAULT-ON in native mode** (`dml_core::engine::stop_engine_enabled(native, None)` → `true`) that stop took the ENGINE down with it: build dead at step 1246/1952, Docker Desktop left answering `500` on every call until a full Quit + `wsl --shutdown` + relaunch. **Two guards, and the first one is NOT a narrowing of the shared predicate** — `verdict_needs_stop` has a second caller, the `wsl --shutdown` path, which is about to power-kill the VM and must keep erring TOWARD stopping or a worldserver dies without a saveall; unifying them would swap one bug for a data-loss bug (`the_two_stop_predicates_stay_separate` pins it). So the watcher gets its own `verdict_worth_auto_stopping`, firing ONLY on `online` — the asymmetry is the argument: declining on a genuinely idle server costs idle RAM, firing on a server mid-maintenance destroys an hour of compute. `starting` is excluded too, being what a rebuild's own `compose up -d` looks like on the way back. Second guard: `MaintenanceGuard`/`maintenance_in_flight` (a DEPTH counter, so overlapping ops can't clear each other's flag) held by `wow_module_rebuild_native`, `wow_update_native` and both unbound arms, which the watcher checks before firing — belt to the verdict's braces, covering the minutes at either end when the server still reads `online`. Residual, deliberately not covered: maintenance driven from OUTSIDE the launcher (the VM's nightly `dml-rebuild-59`) gets only the verdict guard, since an in-process flag cannot see another process.
- Production spawn is exactly `wsl.exe -d dml-arch -u dml -- dml <cmd> --json`; game ids validated `[A-Za-z0-9._-]+` in Rust before any spawn.
- **Self-configuration + tray (2026-07-28):** `src-tauri/src/startup.rs`'s `resolve_and_export()` is the FIRST statement of `run()` — it resolves backend + the three paths (precedence `DML_* env` → `~/.dml/launcher.json` → auto-detect) and exports only what is UNSET. That is why an installed exe works with no env vars, and why native bash children inherit the right paths. `std::env::set_var` is only sound before threads exist, so it MUST stay ahead of `Builder::default()` (whose `.setup()` spawns the backup watcher). Env must stay highest precedence — the parity/bats/CLI-integration suites all inject these vars as override seams. `src-tauri/src/tray.rs` owns the tray (feature `tauri/tray-icon`; capabilities need nothing, `core:default` already grants tray+menu); close HIDES rather than exits (`closeToTray` in launcher.json), status is PUSHED from the frontend poll (Rust has no poller — a second one would duplicate the SOAP client and flap during restarts), and a watchdog releases keep-awake if no push arrives for 2 min. `single_instance.rs` guards via a loopback TCP bind; `autostart.rs` shells `reg.exe` for `HKCU\...\Run`. Backend changes need a relaunch (AppState builds its runner once).
- **First-run backend setup (SHIP-LIST Phase 4, 2026-07-28):** the installer now carries the backend payload (`bundle.resources` in `tauri.conf.json` → `cli/dml`, `cli/lua/party`, `cli/lua/gm`, the six title installers; layout owned by `src-tauri/src/payload.rs`, which fails the test run if the manifest drifts). `backend_status` (chain in `crates/dml-core/src/setup.rs`) answers "what is the FIRST thing missing" and `backend_setup` (`src-tauri/src/provision.rs`) provisions the distro from those bundled resources — streamed over the usual `Channel<Value>` TermEvent seam, idempotent, and it CONSUMES the probe chain both before and after rather than asking its own questions. **`cli/dev-install.ps1` is now the DEV LOOP ONLY** (it no longer hardcodes a repo path — it resolves the repo from `$PSScriptRoot` and translates via `wslpath`); the two step lists cannot literally be one (Rust vs PowerShell), so `provision.rs`'s `dev_install_ps1_installs_the_same_destinations_at_the_same_modes` reads the `.ps1` and fails when they drift.
