- **Self-configuration + tray (2026-07-28):** `src-tauri/src/startup.rs`'s `resolve_and_export()` is the FIRST statement of `run()` — it resolves backend + the three paths (precedence `DML_* env` → `~/.dml/launcher.json` → auto-detect) and exports only what is UNSET — with ONE exception: `DML_BACKEND=auto` is an instruction, not a pin, so the resolved concrete value is written over it (`backend_env_pins`/`backend_value_to_export`). Without that, `resolve` correctly detected Native and `selected()` then read the surviving `auto` through `from_override`'s catch-all to `Wsl`, driving a distro that does not exist — while Settings called the dropdown env-locked so it could not be repaired in the UI. That is why an installed exe works with no env vars, and why native bash children inherit the right paths. `std::env::set_var` is only sound before threads exist, so it MUST stay ahead of `Builder::default()` (whose `.setup()` spawns the backup watcher). Env must stay highest precedence — the parity/bats/CLI-integration suites all inject these vars as override seams. `src-tauri/src/tray.rs` owns the tray (feature `tauri/tray-icon`; capabilities need nothing, `core:default` already grants tray+menu); close HIDES rather than exits (`closeToTray` in launcher.json), status is PUSHED from the frontend poll (Rust has no poller — a second one would duplicate the SOAP client and flap during restarts), and a watchdog releases keep-awake if no push arrives for 2 min. `single_instance.rs` guards via a loopback TCP bind; `autostart.rs` shells `reg.exe` for `HKCU\...\Run`. Backend changes need a relaunch (AppState builds its runner once).
- **`wsl_keepalive.rs` — the Arch AND Wsl backends can host a server at all (2026-08-05).** WSL powers `dml-arch` off ~15s after the last session INTO it exits (see the Gotchas section of the root `CLAUDE.md` — that is the mechanism, this is the fix). Rust holds ONE `wsl.exe -d dml-arch -u dml --exec /bin/sleep infinity` while the server is meant to be running. **Not the 7s frontend poll**, which measurably works and is still the wrong owner: it is a `setInterval` in a webview that HIDES TO TRAY on close, which is exactly where Chromium throttles timers past the 15s budget, it self-skips on `!refreshing`, and nothing in that file says a server's life depends on the interval (the `lifecycle_steps_for_mode` shape). **Intent, not a timer:** `games_start`/`games_restart` declare it BEFORE the work (the command is itself a session, so the clock starts when it exits) and `games_stop` AFTER (releasing first starts the clock mid-`down`). A positive status push ADOPTS a server a previous session started; a negative one deliberately does **not** release — `stopped`/`crashed`/`soap_unreachable` is exactly what a restart looks like from outside, the `restarting` suppression flag lives only in the webview, and holding through a crash is what lets `restart: unless-stopped` put the stack back. So the only routes to "meant to be down" are an explicit stop, a backend change and launcher exit, all of which release — which is what stops an orphaned holder pinning ~1.4 GB of VM. **Arch AND Wsl** (Task 1 of `docs/superpowers/plans/2026-08-05-server-survival.md`, 2026-08-05: both drive the SAME `dml-arch` distro through the same `runner::DISTRO` constant, so both get the identical 15s bug and both now get the holder — `Wsl` is also the default and the only backend the Settings dropdown offers, so it is the backend the user's real server actually runs on), as a `match` so a new backend is a compile error, not a silent opt-out; Native needs nothing (`com.docker.backend` already holds `docker-desktop`). **Never leaks:** `RunEvent::Exit` releases; the impolite exits are covered by a `KILL_ON_JOB_CLOSE` job object bound with a bare kernel32 `extern "system"` like `power.rs` — PROVEN with a control (same harness without the job: the holder SURVIVED an abrupt parent kill; with it, it died). `release()` hands the child to `dml_core::proc::abandon`, never `wait()`s it, because the watchdog holds the state mutex while releasing. **The bound is checked BEFORE the attempt, not in the error arm** — the error arm is the obvious placement and only bounds a session that will not SPAWN, while what a sick distro actually produces is a `wsl.exe` that starts fine and exits a moment later, which re-spawned forever (`a_holder_that_always_dies_immediately_also_hits_the_bound` found it on its first run). Reporting: `wsl_keepalive_status` re-derives the verdict from live state and a shell banner names the reason AND the consequence; re-read on mount as well as on the event, because a module-level store dies with a webview reload (the soap-autosetup lesson). Live gate: `cargo test -p launcher --lib wsl_keepalive::tests::live_ -- --ignored --nocapture` proves BOTH halves — survived 62.1s (4.1x the deadline), died 16.5s after release. Half one alone would pass against `wsl --list` polling, which is measured not to work.
