Why this file exists.  Section 1 of README.md says the 2026-09-04 `sweep_driver2.py` abort
(exit 134, SIGABRT at interpreter shutdown) is gone on `cfb4c04f` *because* `d2b963d5` made
`runner.py::stream()` register its generators in `_LIVE_STREAMS` and close what is left from
`_close_abandoned_streams()` at `atexit`.  What the run itself established is a correlation:
exit 134 at `81d7311e`, exit 0 at `cfb4c04f`, the same driver, `stream()` changed in between.
This is the mutation that makes it a cause.  Run on 2026-09-05 (21:48 UTC / 23:48 CEST) on
`yulon-fedora`, on a throwaway `git clone --shared` of the box's own checkout, checked out at
`cfb4c04f367536375abf6382694a1f800c468b8a`, with `__pycache__` purged on both sides of every
transition (a same-length edit can otherwise reuse stale bytecode).  The throwaway was removed
afterwards and the box's `~/dads-mmo-lab` was left clean.

Note the interpreter: this is Python **3.13.15** on Fedora, not the 3.12.3 the gate ran on
`yulon-ubuntu`, and the 09-04 measurement in `runner.py`'s own docstring was CPython 3.11.15 on
m910q.  The hazard and the fix reproduce on all three.

    """Abandoned-`stream()` probe: take five lines off a live generator and never close it."""

    import sys

    sys.path.insert(0, "/home/pk/mut710/pylauncher")

    from yulon import runner

    CMD = ["sh", "-c", "i=0; while :; do echo line $i; i=$((i+1)); sleep 0.2; done"]

    G = runner.stream(CMD)
    n = 0
    for line in G:
        n += 1
        if n >= 5:
            break
    print(f"took {n} lines; abandoning the generator without close()", flush=True)

`G` is a module global on purpose: refcounting must not collect the generator early, so the
finalisation has to happen at interpreter shutdown -- the shape `sweep_driver2.py` hits when it
takes five lines off `logs_source()` and `break`s.

--- what it settles -----------------------------------------------------------------------

One line, one behaviour: with `atexit.register(_close_abandoned_streams)` in place the abandoned
generator is closed at exit and the probe returns 0; with that registration replaced by a no-op
the same probe dies with the same fatal error, in the same function, that the 2026-09-04 run
recorded -- `_enter_buffered_busy` on the `BufferedReader` the `_drain_stderr` daemon thread is
blocked in.  Restoring the line restores exit 0.  So README.md section 1's "the abort went away
because the shared layer was fixed" is a measured cause here, not an inference from two exit
codes.

It does NOT establish that nothing else in the 153-line `runner.py` delta contributes; it
establishes that this registration is necessary for the probe to survive shutdown at `cfb4c04f`.
