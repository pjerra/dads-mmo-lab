# 8.4d — Play, WoW Tortoise — the live gate plan

Written 2026-09-08, after the adversarial review of 8.4d's code half. The
evidence folder this plan produces is `pyplan/gates/8.4d-tortoise-m910q-<date>/`
and it does not exist yet: the box has never been run.

**Why this file exists at all.** The plan it corrects was never in the
repository. It lived in the structured output of the run that wrote 8.4d's code
— a task record in a scratchpad — so the review's finding 6 ("find the plan and
correct it in place") had no place to point at. Left there it would be gone the
day that scratchpad is cleared, and the next person to open this box would plan
it again from nothing. So the plan is checked in, with the review's three
corrections applied and marked, and it is a plan rather than evidence: nothing
below has been run.

Every source citation was re-read on `m910q` on 2026-09-08 against
`~/tortoise-server/src/tortoise-wow` and that install's own `etc/mangosd.conf`,
read-only, with nothing started. Where the earlier plan's line number was off by
two, the number here is the one that was read.

## Ground (not steps)

**G1.** One server at a time on `m910q` is the owner's rule. Whatever stack is
up when this box starts must come down first, and the Tortoise stack brought up.
Announce every action on the activity terminal (`~/bin/claude-say`) before doing
it.

**G2.** `docker attach` the tortoise worldserver and send `server info`; a
revision line and `Players online: N` must come back. Every "the command did
nothing" reading below is ambiguous without this, and the console is the ONLY
channel here (the entry's `operations.channel` is `attach`).

**G3.** Pick playerbot characters — one with `online = 1` and one with
`online = 0` — and record, with timestamps: guid, name, level, map,
position_x/y/z, at_login, corpse row, mail row count, and the count from
`SELECT COUNT(*) FROM tw_char.character_inventory WHERE guid = ? AND bag = 0
AND slot < 19`. Every step below asserts a CHANGE against this reading; that is
what makes them proofs rather than screenshots. `RandomPlayerbotMgr` re-levels
and re-positions its bots, so read within seconds or pull the bot out of the
rotation first.

## Steps

**S1 — proves: this tree has no console route that puts an EXISTING character at
a level somebody picks.** *(Rewritten. The review's finding 1: the first version
of this step did not press the route that refutes the box's own sentence, and
the sentence it left standing was false.)*

Ground: G2, and the online bot's level from G3.

Send, on the console, and record the answer to each:

1. `levelup <onlinebot> 1` — must be refused. It is
   `{ "levelup", SEC_DEVELOPER, false, &ChatHandler::HandleLevelUpCommand, … }`
   at `src/game/Chat/Chat.cpp:923`, and `CliHandler::isAvailable`
   (`Chat.cpp:3723-3731`) returns false on `!cmd.AllowConsole` at `:3726-3727`
   before it looks at the security level at all.
2. `character level <onlinebot> 60` — must answer that there is no such
   subcommand. `characterCommandTable` (`Chat.cpp:151-165`) carries deleted,
   erase, getname, diffitems, reputation, hasitem, fillflys, clean, itemlog,
   mail and inactivity, and no `level` row and no `rename` row.
3. `rndbot <onlinebot> level 60` — must leave `characters.level` unchanged.
   `.rndbot` IS console-legal — `{ "rndbot", SEC_PLAYER, true, … }` at
   `Chat.cpp:1012` — and `m_botCommandHandlers["level"]` and `["levelup"]`
   (`modules/mod-playerbots/src/playerbot/PlayerbotMgr.cpp:335-336`) both reach
   `HandleBotLevelUp` (`:3159`), whose entire body is
   `PlayerbotFactory factory(bot, bot->GetLevel()); factory.Randomize(true, false);`
   — it never reads the parameter it was handed.
4. `rndbot init <onlinebot>` — records what it does. `HandleBotInit` (`:3094`)
   builds with `master ? master->GetLevel() : bot->GetLevel()`, and a console
   call has no master.
5. **`rndbot create level=60 class=1 race=1 name=<a name nobody has> …`** — this
   one is EXPECTED TO WORK, and that is the point of the step. The console
   command falls through `RandomPlayerbotMgr::HandlePlayerbotConsoleCommand`
   (`RandomPlayerbotMgr.cpp:3612`) at `:3743` into
   `PlayerbotHolder::HandlePlayerbotCommand`, whose `m_holderHandlers["create"]`
   (`PlayerbotMgr.cpp:303`) is `HandleCreate` (`:2593`) — no security check and
   no master requirement, unlike `HandleGroup` at `:2603` — which calls
   `CreateBot` (`:2350`, its own comment: *"Allow null master for RA/console
   usage"*, `:2352-2353`). `CreateBot` parses `level=` at `:2389` and runs
   `SetLevel(level)` inside `if (level > 1)` at `:2497-2510`. Assert a NEW row
   in `tw_char.characters` at level 60 — and assert that no row that existed at
   G3 changed its level.

Assert at the end: no command in this list moved an existing character to a
chosen level, and the one that reached a chosen level made a character that was
not there before. That is the clause the shipped sentence now rests on, and it
is the only thing S2 is allowed to claim.

## Blocked, and why (carried forward unchanged, re-checked)

**B1 — a SOAP channel for wow-tortoise.** This build has no SOAP source in
`src/mangosd` and no `SOAP.*` key in `etc/mangosd.conf`; the checkout's HEAD
(`7f2957e0e5f8`, 2026-09-02) predates the fork's SOAP commit (`3f9a0622`,
2026-09-07). Everything above runs over `docker attach`, which is what the entry
declares.

**B2 — setting an arbitrary level on an existing character from the app.**
`.levelup` is the only command that writes one and its `AllowConsole` is false
(`Chat.cpp:923`). That is not a permission an install can be configured into:
`ChatCommand` (`Chat.h:62-74`) carries `AllowConsole` as a member of its own,
and the one function that applies a row of the `command` DB table over a
command, `SetDataForCommandInTable` (`Chat.cpp:1741-1761`), assigns
`SecurityLevel`, `Help` and `Flags` and never touches it. This is not a clause
of 8.4d — its absence IS the box — but it stays blocked even after a rebuild
unless the fork changes that table row.

**B3 — acting on a character a person made.** This install holds bot characters
only; making one needs a client login, which needs a working account password,
and `.account set password` on this binary hashes over an empty username and
locks the account out while reporting success (fixed upstream in `3a8472e6` on
2026-09-07, not in this binary). So every step above acts on a playerbot, and
any clause worded "for a human character" is deferred to the rebuild.

**B4 — any step that needs the world to hold still.** The bot manager re-levels,
re-gears and re-positions its bots, which is why every step above records the
timestamp of its reading and why a bot that cannot be read within seconds of the
command should be taken out of the rotation first.
