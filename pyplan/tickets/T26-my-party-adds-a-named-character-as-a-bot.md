## Spec

**What the player gets.** Beside "Add a bot of a chosen class", My Party gets "Add this character…": a list of characters the module would accept for THIS master under the running conf -- own account's other characters, guild mates, linked accounts -- each row `name, level, class, account/guild, why allowed`, online ones greyed with "logged in", and the master's added-bot count against `MaxAddedBots`. A press whispers the bridge's `dml_botadd <master> <name>`; the bridge runs `.playerbots bot add <name>` as the master and answers over the SOAP result with the module's own sentence; the panel polls the group table as `add_bot` does and reports in the app's voice. A second control, "Link an account…", writes a `playerbots_account_links` row (master's account, the other account by name) with a confirmation naming both and the fact that the module treats every character of that account as addable from then on; this is the friends-and-family route the owner asked for, and it is a write, so the ledger gets a row.

**The hard fact the spec is built on:** `bot add` only works from a real, non-bot player session. So the live half needs a client-driven master (the win11 VM's client, `driving-a-wow-client-unattended.md`), and the bridge script must run the command as that player. The unit half: the picker's filter (three reads, the five rules spelled from the source lines above, `online` and `MaxAddedBots` first), the bridge script and its Python seam with the sentence grammar pinned to the shipped Lua as T13 did, `Link an account` with its write and refusal (unknown account name, own account, already linked). The live half: an alt on the same account added; a guild mate added; a linked account's character added; an online character refused; the sixth rule (the addclass pool) already covered by 8.6's existing route. WotLK only; the other trees do not offer the control.

**Not in scope:** cross-faction (unchecked in the module; measure first), `BotAutologin` (a conf change the owner has not asked for), `KeepAltsInGroup`.

**Hand:** Opus, two halves, worktree branched from `yulon-phase8b`; file set: `pylauncher/lua/party/dml_botadd.lua` (new), `party.py` (the seam, `BRIDGE_SCRIPTS`, the picker reads, the link write), `party_panel.py` and `controller_view.py` at the My Party group only, `pyplan/write-ledger.md` (one row), their tests, and a NEW gate folder for the live half. **Box:** `yulon-ubuntu2` plus a client seat on `yulon-win11`, on the lead's word; the deploy needs a world restart.
